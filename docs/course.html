Chapter 0 / Start here / 10 min

How to use this course

A ground-up walk through the egocentric_splats pipeline: from “what is a focal length” to “here is the exact line where the Gen 2 port fixes a silent data-loss bug.” About fourteen hours of focused study, spread over as many sittings as you like — beginning with a complete hands-on run of the pipeline before any theory.

What this covers

This repository takes a video recorded on a pair of Project Aria smart glasses and turns it into a 3D Gaussian Splat — a reconstruction of the room you can fly a virtual camera through. Between those two things sit about ten thousand lines of Python, four large data files, and a dozen conventions that are obvious once you know them and impenetrable before.

The course is built in nine parts, and they are ordered deliberately:

Code and data live in different places

This trips people up constantly, so it is worth stating once and plainly. The repository holds only code. Nothing the pipeline produces is written inside it, except the trained model under output/. $PROC
Where preprocessing writes. On the reference machine: /home/sun/aria/processed/, and not inside the repository. The same directory is called --output_root when preprocessing and scene.data_root when training — two flag names, one folder. If they disagree, training reports an empty scene while preprocessing looks perfectly healthy.
egocentric_splats/
The repository itself — code, and the trained output/ tree. Paths shown with this prefix are files you can open and read.

Chapter 0.1 / Part 0 · Run it once / 15 min

How to read a command

Before any of the rest matters, you need to be able to look at a line like python foo.py --bar 1008 --baz "some path" and know exactly what every piece is doing. That is this chapter. No pipeline knowledge required.

Anatomy of a command

Every command you will run in this course has the same four-part shape:

python  scripts/extract_aria_vrs.py  --rectified_rgb_focal  1008
└──┬─┘  └──────────┬──────────────┘  └─────────┬────────┘  └─┬┘
   1               2                           3             4
1 · the program
python. The thing that runs. Could also be conda, ls, bash.
2 · the argument
What the program should work on — here, the script file to execute.
3 · a flag
A named input, always starting with --. Also called an option or a switch.
4 · the flag's value
Separated from the flag name by a space.
What a flag actually is

A flag is a labelled slot the program's author decided you can fill in. Because each one is named, order does not matter — --focal 1008 --height 1512 and --height 1512 --focal 1008 are identical.

If you leave a flag out, the program uses its built-in default. Those defaults are visible in the source: every parser.add_argument(...) call near the bottom of scripts/extract_aria_vrs.py declares one flag, and most carry default=.

A few flags take no value at all. These are on/off switches — mentioning them turns the thing on:

# with the switch: regenerate everything
python scripts/extract_aria_vrs.py --overwrite

# without it: skip anything already done
python scripts/extract_aria_vrs.py

--overwrite and --visualize are both switches. You never write --overwrite true.

Paths: telling a program where a file is

A path is a file or folder's address. There are two kinds and the difference matters.

absolute
Starts with /, e.g. /home/sun/aria/my.vrs. Reads from the root of the disk. Means the same thing no matter where you are standing.
relative
Does not start with /, e.g. scripts/extract_aria_vrs.py. Interpreted relative to your current directory. Means different things depending on where you are.

Three commands let you navigate:

pwd                 # "print working directory" — where am I right now?
ls                  # list what is in here
cd /home/sun/aria   # "change directory" — go there

~ is shorthand for your home folder, so ~/aria and /home/sun/aria are the same place.

The rule this course uses

Always cd into the repository first, then use a relative path for the script and absolute paths for your data:

cd ~/Desktop/aria_proj/egocentric_splats
python scripts/extract_aria_vrs.py --trajectory_file /home/sun/aria/mps_.../slam/closed_loop_trajectory.csv

Two ways to get a path without typing it wrong. Tab completion: type the first few characters and press Tab — the shell finishes it, and if nothing happens the thing you typed does not exist, which is itself useful information. Drag and drop: in most terminals, dragging a file from your file manager into the window pastes its absolute path.

Quotes, and why they are not optional here

The shell splits your command on spaces. So a path containing a space gets torn in half:

# BROKEN — the shell sees two separate arguments
--vrs_file Test recording_20260804.vrs

# CORRECT
--vrs_file "Test recording_20260804.vrs"
This will happen to you

Aria Studio names recordings with spaces in them by default — Test recording_20260804_195027.vrs. Quote every path, every time, even when it has no spaces. It costs nothing and removes an entire category of confusing error.

Splitting one command over many lines

The commands ahead have a dozen flags and would be unreadable on one line. A backslash at the end of a line means this command continues below:

python scripts/extract_aria_vrs.py \
    --input_root  "/home/sun/aria" \
    --output_root "/home/sun/aria/processed" \
    --vrs_file    "my_recording.vrs"

This is one command, not three. Two rules: the last line has no backslash, and nothing may follow a backslash — not even a single trailing space. A stray space after a \ is a genuinely common and baffling failure.

Variables: naming a path once

You will reference the same folders repeatedly. Rather than retyping them, give them names:

export REC=/home/sun/aria
export SCENE=Outside_20260812_141244
export MPS="$REC/mps_${SCENE}_vrs/slam"

export NAME=value creates it; $NAME uses it. Note the third line uses the first two — variables build on each other.

$NAME
Normal use. Fine when a space or / follows.
${NAME}
Braces needed when text runs straight on. $SCENE_vrs would look for a variable called SCENE_vrs; ${SCENE}_vrs is what you meant.
"$NAME"
Always quote it in a command. If the value contains a space, unquoted use breaks exactly as above.

Variables live only in the terminal window where you set them, and vanish when you close it. Open a new window, set them again.

Check before you commit hours

Print a variable with echo, and prove the path exists with ls:

echo "$MPS"
ls -la "$MPS"

If a variable was never set it expands to nothing, so "$MPS/online_calibration.jsonl" silently becomes /online_calibration.jsonl and you get a file-not-found error that points at the wrong place entirely. Ten seconds of echo saves that.

Keeping a log

You will see this at the end of the preprocessing command:

... 2>&1 | tee "$PROC/preprocess.log"

Three pieces. 2>&1 merges the error stream into the normal output stream so both get captured. | pipes that combined output into the next program. tee writes it to a file and still prints it to your screen.

This matters because preprocessing prints validation numbers that scroll past over several hours and cannot be recovered afterwards. Chapter 0.4 tells you which lines to look for.

Check yourself

What is wrong with --input_root ~/my recordings?

The space. The shell passes ~/my as the value and then treats recordings as a separate argument, which the program will either reject or silently ignore. Write --input_root "~/my recordings" — though note that ~ inside quotes is not expanded by every shell, so the safest form is the full absolute path in quotes: "/home/sun/my recordings".

You run a command and get No such file or directory: /online_calibration.jsonl. What happened?

Your $MPS variable was empty — probably you set it in a different terminal window, or closed and reopened the terminal. The variable expanded to nothing, leaving just the trailing part of the path. Run echo "$MPS"; if it prints a blank line, set your variables again.

Does --rectified_rgb_focal 1008 --rectified_rgb_size 1512 differ from the reverse order?

No. Flags are named, so order is irrelevant. Only positional arguments — like the script filename after python — depend on position, and this pipeline has just one of those.

Chapter 0.2 / Part 0 · Run it once / 15 min

Setting up the environment

One conda environment runs the entire pipeline — preprocessing and training both. Four commands to build it, three checks that prove it works.

Build it

# create the environment (once, ever)
conda create -n ego_splats python=3.10 -y

-n names it. -y answers yes to the prompt. Python 3.10 is what the repository is tested against — 3.11 usually works, but if a wheel fails to install, the version is the first thing to change back.

If you already have the environment, or have just made it, activate it:

conda activate ego_splats
How you know it worked

Your prompt gains a prefix: (ego_splats) sun@machine:~$. That prefix is the single most useful thing on your screen — the most common cause of a mysterious ImportError is simply not having activated.

Activation applies to one terminal window. Every new window starts fresh and needs conda activate ego_splats again.

Install the packages

conda activate ego_splats
cd ~/Desktop/aria_proj/egocentric_splats

# 1. PyTorch first, from the CUDA-specific index
pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu128

# 2. everything else
pip install -r requirements.txt

Why torch first. requirements.txt asks for torch>=2.6.0 without specifying a CUDA build. If you let it install torch, pip fetches whichever default build PyPI offers, which may not match your GPU. Installing the CUDA build first satisfies the requirement, so step 2 leaves it alone.

Which cu number. Run nvidia-smi and read the CUDA version in the top-right of the output, then pick the closest index from pytorch.org. cu128 is what this repository was tested with; cu121 is the safe choice on older drivers.

One environment, not two

The README describes two environments — a light aria one for preprocessing and ego_splats for training. You do not need the split. requirements.txt already includes projectaria-tools, opencv-python, rerun-sdk, pandas and gsplat, so this single environment covers both halves. The two-environment setup only helps if you want to preprocess on a machine with no GPU.

Prove it works

# 1. GPU visible to PyTorch?
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"

# 2. the two imports that break preprocessing
python -c "import cv2, projectaria_tools; print('imports ok')"

# 3. the driver and its CUDA version
nvidia-smi
2.6.0+cu128 True
imports ok

True is the one that matters. If it says False, PyTorch cannot see your GPU — almost always the wrong torch build, so reinstall step 1 with a different cu index.

The OpenCV trap

scripts/aria_utils.py imports cv2 at the top of the file, before any function runs. An environment that has projectaria_tools but not OpenCV therefore dies instantly at import — after you have set up all your paths and pressed enter, but before it does a single second of work. Check number 2 above exists for exactly this.

One more thing before training

gsplat — the CUDA rasterizer from Chapter 6 — compiles its GPU kernels the first time you train, not at install. That first run therefore pauses for several minutes with no output. It needs the CUDA compiler available:

nvcc --version        # should print a CUDA release
echo "$CUDA_HOME"     # should print a path, e.g. /usr/local/cuda

If nvcc is missing you have the runtime but not the toolkit; install cuda-toolkit for your distribution and set CUDA_HOME to where it landed.

What needs what

Preprocessing is CPU-only. It runs on any machine, including Apple Silicon, with no GPU at all.

Training needs an NVIDIA GPU. gsplat's rasterizer is CUDA and has no CPU or Metal backend — there is no slow fallback, it simply will not run.

Check yourself

You open a new terminal tomorrow and get ModuleNotFoundError: No module named 'torch'. Why?

You did not activate the environment in that window. Run conda activate ego_splats and check your prompt shows (ego_splats). Activation is per-window and does not persist.

torch.cuda.is_available() prints False but nvidia-smi works fine. What now?

The driver is fine; PyTorch is the wrong build — you have a CPU-only or mismatched-CUDA wheel. Reinstall with the index URL matching the CUDA version nvidia-smi reports, then re-check. Note that installing requirements.txt before torch is the usual way to end up here.

Can you preprocess on a laptop with no GPU and train elsewhere?

Yes, and it is a sensible split. Preprocessing is pure CPU. Copy the resulting processed/<recording>/ folder to the GPU machine — but be aware it contains two symlinks (Chapter 13), so copy with a tool that follows them, or copy the MPS folder too and recreate the links.

Chapter 0.3 / Part 0 · Run it once / 15 min

Your recording's five facts

Two of the preprocessing flags are numbers you have to work out from your own recording. Here is how to find every path and compute every number, before running anything that takes hours.

What you should have on disk

You have already recorded and run MPS, so your folder looks roughly like this:

~/aria/
├── Outside_20260812_141244.vrs              ← the recording
└── mps_Outside_20260812_141244_vrs/
    └── slam/
        ├── closed_loop_trajectory.csv       ← needed
        ├── online_calibration.jsonl         ← needed
        ├── semidense_points.csv.gz          ← needed
        ├── semidense_observations.csv.gz    ← needed
        └── open_loop_trajectory.csv           ignored by this pipeline

The MPS folder name is derived from the VRS filename with dots replaced by underscores — that is why it ends in _vrs.

Name your paths

Set these once per terminal window. Everything afterwards refers back to them:

export REC=/home/sun/aria
export SCENE=Outside_20260812_141244
export MPS="$REC/mps_${SCENE}_vrs/slam"
export PROC="$REC/processed"
mkdir -p "$PROC"

# prove they are right before going further
ls -la "$REC/$SCENE.vrs"
ls -la "$MPS"
What $SCENE must be

The VRS filename without the .vrs extension. The pipeline uses it to name the output folder, and reconstructs the filename by appending .vrs itself. Get this exactly right, including capitalisation.

The second ls must show all four required files. If semidense_observations.csv.gz is missing, preprocessing still runs but produces no sparse depth at all — it prints one line saying so and carries on.

Print the facts

Paste this whole block into your terminal. It reads your recording and prints everything you need:

python - <<'EOF'
import os
from projectaria_tools.core import data_provider, mps

vrs = f"{os.environ['REC']}/{os.environ['SCENE']}.vrs"
p     = data_provider.create_vrs_data_provider(vrs)
calib = p.get_device_calibration()

print("device        ", calib.get_device_version().name)
print("cameras       ", list(calib.get_camera_labels()))

sid = p.get_stream_id_from_label("camera-rgb")
n   = p.get_num_data(sid)
img, rec = p.get_sensor_data_by_index(sid, n // 2).image_data_and_record()
a = img.to_numpy_array()
print("rgb frames    ", n)
print("rgb resolution", a.shape[1], "x", a.shape[0], "  (width x height)")

calibs = mps.read_online_calibration(f"{os.environ['MPS']}/online_calibration.jsonl")
for c in calibs[0].camera_calibs:
    r = c.get_readout_time_sec()
    print(f"readout {c.get_label():18s} {0.0 if r is None else r * 1e3:6.2f} ms")

Why it decodes a real frame

The script reads the resolution from an actual decoded image in the middle of the recording rather than from the calibration object. That is deliberate, and it copies what the pipeline itself does — to_frame_json carries the comment "the calibration image size might be incorrect due to API issue" and takes its dimensions from the decoded array. Trust the pixels.

Zero readout on the SLAM cameras is correct, not missing — they are global shutter (Chapter 4).

Turning the resolution into two flags

You now need two numbers for RGB: an output height and a focal length.

Step 1 — height

Use your recording's native height. From the output above, that is 1512. The width is derived automatically from the source aspect ratio, so at native height you get back your native width — no resampling, no invented pixels, no discarded detail.

Step 2 — focal

Focal length decides how much of the scene fits into that image. The relationship from Chapter 1:

The formula 
FOV = 2 · atan( (W / 2) / focal )      rearranged:      focal = (W / 2) / tan(FOV / 2)

where W is the output width. Useful shortcut: when focal = W / 2 the horizontal FOV is exactly 90°.

Compute it for whatever FOV you want:

python -c "import math; W=2016; fov=90; print(round((W/2)/math.tan(math.radians(fov)/2)))"
1008

The trade, on a 2016-wide output:

FocalHorizontal FOVWhat you get
100890.0°Start here. Balanced; matches what the Gen 1 defaults effectively produced
756106.3°More of the room per frame, less detail per degree
151267.4°Sharp but narrow; discards a lot of what the lens saw

Step 3 — the SLAM cameras

Less thought required. Gen 2 SLAM is 512×512 with a 119° lens; focal 180 at height 512 keeps about 110° of it. Use those unless you have a reason not to.

Do not inherit the script's defaults blindly

run_vrs_preprocessing_gen2.sh ships --rectified_rgb_focal 1280 --rectified_rgb_size 1920. Those are correct for profile8 (2560×1920). If your recording is profile10 (2016×1512), they upsample every frame to 2560×1920 — 30% more disk, memory and training time for zero extra information, with no warning of any kind. Chapter 3 covers why.

Write these down

Four numbers, and you will need them again:

export RGB_FOCAL=1008
export RGB_HEIGHT=1512
export SLAM_FOCAL=180
export SLAM_HEIGHT=512

The RGB pair ends up embedded in your output folder name — camera-rgb-rectified-1008-h1512 — and the training command must repeat that folder name exactly. Getting them consistent is the single most common source of a failed training launch.

Check yourself

Your recording prints rgb resolution 2560 x 1920. What two numbers do you use?

Height 1920 (native), and focal 2560/2 = 1280 for 90°. That is profile8, and those happen to be the shipped script's defaults — correct here, wrong for profile10.

Why set the height to the native value rather than something larger?

Because resampling to a larger grid interpolates between real pixels — it cannot add detail that was never captured. You would pay proportionally more disk, GPU memory and time per training iteration for a blurrier version of the same information.

You want a wider field of view without changing file size. What do you change?

Lower the focal, keep the height. Focal 756 at width 2016 gives 106.3° in exactly the same number of pixels — the same scene detail spread thinner, plus more of the room. Push too far and you get black corners where the output asks for directions the lens never saw.

Chapter 0.4 / Part 0 · Run it once / 20 min

One full pass, start to finish

Five steps. Everything is explained flag by flag. Budget two to four hours of CPU for preprocessing and several hours of GPU for training, and about 50 GB of disk.

Step 1 — set everything up

conda activate ego_splats
cd ~/Desktop/aria_proj/egocentric_splats

export REC=/home/sun/aria
export SCENE=Outside_20260812_141244
export MPS="$REC/mps_${SCENE}_vrs/slam"
export PROC="$REC/processed"
export RGB_FOCAL=1008
export RGB_HEIGHT=1512
mkdir -p "$PROC"

Substitute your own values from Chapter 0.3. Confirm with ls -la "$MPS" before continuing.

Step 2 — preprocess

python scripts/extract_aria_vrs.py \
    --input_root  "$REC" \
    --output_root "$PROC" \
    --vrs_file    "$SCENE.vrs" \
    --rectified_rgb_focal         "$RGB_FOCAL" \
    --rectified_rgb_size          "$RGB_HEIGHT" \
    --rectified_monochrome_focal  180 \
    --rectified_monochrome_height 512 \
    --online_calib_file           "$MPS/online_calibration.jsonl" \
    --trajectory_file             "$MPS/closed_loop_trajectory.csv" \
    --semi_dense_points_file      "$MPS/semidense_points.csv.gz" \
    --semi_dense_observation_file "$MPS/semidense_observations.csv.gz" \
    2>&1 | tee "$PROC/preprocess_$SCENE.log"
FlagWhat you passWhat it does
--input_rootfolderWhere to look for the recording
--vrs_filefilename onlyWhich recording, relative to --input_root
--output_rootfolderWhere all output goes. A subfolder named after the recording is created inside

Both focal flags default to −1

Which means skip that camera. Omit them both and the command runs, prints a little, and produces nothing at all. If a run finishes suspiciously fast, this is why.

Three lines to watch for as it runs. They are your evidence that each stage did real work:

Detected Gen2 device: rgb=camera-rgb, slam=['slam-front-left', ...]
camera-rgb: a total of 4676 number of frames.
==> slam-front-left: matched observations for 1571/4717 frames (33.3%)
label line
Confirms the device was detected and all cameras resolved.
frame count
Slightly below the VRS total is normal — frames outside the trajectory window have no pose and are dropped.
match rate
The important one. Four of these, one per SLAM camera. ~33% is correct. 0% means depth supervision is silently empty.

You can stop and restart safely — every stage skips work it has already done. Add --overwrite to force a redo.

What a camera does to the world

A camera turns 3D points into 2D pixels. Four numbers describe how. Learn those four and half the vocabulary of this repository stops being jargon.

The pinhole model

Imagine a sealed box with a tiny hole in one face and film on the opposite face. Light from a point in the world travels in a straight line through the hole and lands on exactly one spot on the film. That is a pinhole camera, and despite being a 19th-century toy it is the model essentially all of computer vision uses.

Set up coordinates with the pinhole at the origin. The camera looks down the +Z axis. +X is to the right, +Y is down. (Y-down feels wrong the first time — it is inherited from image files, whose first row is the top row. Every convention in this repository uses it.)

Now the part that trips people up. The real sensor sits behind the pinhole, at z = −f, and the image it forms is upside down — light from below the optical axis lands above it. Carrying that flip through every equation is a nuisance, so computer vision universally adopts a convenient fiction: an imaginary image plane in front of the pinhole, at z = +f. The image there is the same size and the right way up, and the formulas lose their minus signs. Everything from here on means that front plane.

The two triangles are similar because they share the angle at the pinhole, so v/f = Y/Z. Rearranged, that is the entire projection in two lines:

u = f * X / Z
v = f * Y / Z

Divide by depth. That is the whole of perspective: things twice as far away appear half as large. Notice that Z disappears from the result — from a single pixel you cannot recover how far away the thing was. Recovering it is what the rest of this pipeline is about.

The four numbers

Real image coordinates count pixels from the top-left corner, not from the optical centre, so the formula grows two offsets. And because pixels are not always perfectly square, the focal length gets a separate value per axis:

u = fx * X / Z + cx
v = fy * Y / Z + cy
Definition · intrinsics

fx, fy — focal length, measured in pixels. Not millimetres. A focal length of 1008 means: an object one unit wide, one unit away from the camera, spans 1008 pixels.

cx, cy — the principal point: where the optical axis pierces the image, in pixel coordinates. Usually near the image centre.

These four numbers together are the camera's intrinsics — everything about how it maps directions to pixels, independent of where it is standing.

They are conventionally packed into a 3×3 matrix called K:

      ⎡ fx   0   cx ⎤
  K = ⎢  0  fy   cy ⎥
      ⎣  0   0    1 ⎦

You will see exactly this constructed in the repository, twice, in scripts/extract_aria_vrs.py:

# extract_aria_vrs.py — create_visible_depth_map()
calibK = np.array(
    [[frame["fx"], 0, frame["cx"]],
     [0, frame["fy"], frame["cy"]],
     [0, 0, 1]]
)

Multiplying K by a 3D point in camera coordinates gives (fx·X + cx·Z, fy·Y + cy·Z, Z). Divide the first two by the third and you get exactly the u, v above. That final division is called the perspective divide, and it is the one step in the whole chain that is not a matrix multiply.

Field of view, and why focal length is a choice

An image is finite. If it is W pixels wide with focal length f, then the widest ray it can capture is the one hitting the left or right edge, at W/2 pixels from the centre. Basic trigonometry:

Formula · horizontal field of view 
FOV = 2 · atan( (W / 2) / f )

This single formula governs a decision you have to make before running preprocessing. Some worked values, all from the real Gen 2 RGB sensor at 2016 pixels wide:

FocalWidthHorizontal FOVMeaning
1008201690.0°Balanced. Each pixel covers a small angle — crisp detail.
7562016106.3°Wider view, same pixel count, so each pixel covers more angle — softer.
1512201667.4°Narrow and detailed. You throw away the edges of what the lens saw.

Lower focal, wider view, less detail per degree. Higher focal, narrower view, more detail per degree. There is no free lunch: the pixel budget is fixed by the sensor, and focal length decides how you spend it across the scene.

Why you get to choose at all

A camera's real focal length is a physical property of its lens — you cannot change it after the fact. But this pipeline resynthesises each image as if it had been taken by a different, idealised camera (Chapter 3). That synthetic camera's focal length is yours to pick, which is why --rectified_rgb_focal is a command-line flag.

Depth, and the word “z”

Throughout this codebase, z means distance along the camera's viewing axis — not distance from the camera. A point 3 m directly ahead and a point 3 m ahead but far off to the side have the same z but different Euclidean distances. This is sometimes called ray depth versus plane depth; everything here uses plane depth, because that is what falls out of the projection maths naturally.

Two consequences you will meet later:

  • z > 0 means “in front of the camera.” A point behind the camera has negative z, and the projection formula happily divides by it, producing a sign-flipped u, v that can land inside the image. Chapter 15 shows a real bug in this repository caused by forgetting to check that.
  • Inverse depth — 1/z — appears in the depth loss. It compresses far distances: everything past 20 m maps into a narrow band near zero, which prevents distant, poorly-measured points from dominating the error.

Check yourself

A camera has fx = 1200 and an image 2400 pixels wide. What is its horizontal FOV?

2 · atan(1200/1200) = 2 · 45° = 90°. When the focal length equals half the width, the FOV is exactly 90 degrees. That is a handy landmark to keep — the Gen 1 defaults in this repo (focal 1200, width 2400) sit exactly there.

Why can't you recover a point's distance from one image?

Because u = fx·X/Z + cx only constrains the ratio X/Z. Every point along the ray through that pixel projects to the same pixel. You need a second view from a different position (a baseline) to triangulate — which is exactly why Chapter 25 tells you to walk rather than pivot while recording.

If you double the output height but keep the focal length, what happens to the FOV?

Vertical FOV roughly doubles in extent (not in degrees — atan is nonlinear), because you have added pixels at the top and bottom that see further out. This is why the flag --rectified_rgb_size (a height) and --rectified_rgb_focal must be chosen together; changing one alone changes the FOV.

Chapter 2 / Part I · Seeing / 35 min

Where the camera is

Chapter 1 assumed the camera sat at the origin. It doesn't. This chapter is about rigid transforms — the single most important idea in the repository, and the source of most confusion when reading it.

Frames of reference

A “point in 3D” is meaningless without saying relative to what. This pipeline juggles three answers:

world
A fixed frame, established by the SLAM system when tracking starts. Its origin is arbitrary but it never moves. The reconstructed scene lives here.
device
Attached to the glasses. Moves with your head. Its origin is a reference point on the frame of the glasses.
camera
Attached to one specific lens. There are five on Gen 2 (one RGB, four SLAM), each rigidly bolted at a slightly different place and angle on the device.

The same physical corner of a table has three different coordinate triples depending on which frame you name. Converting between them is what a rigid transform does.

Rotation and translation

A rigid transform does two things and only two things: it rotates, and it shifts. It never stretches, mirrors, or bends. Written out:

p_target = R · p_source + t

where R is a 3×3 rotation matrix and t a 3-vector translation. A rotation matrix is not any old 3×3 — its columns are unit-length and mutually perpendicular, which is exactly the property that makes it rotate without distorting. There are three degrees of freedom in R and three in t, so six numbers describe any rigid placement of any object in space.

Definition · SE(3)

The set of all rigid transforms is called the special Euclidean group in 3 dimensions, written SE(3). When you see sophus.SE3 in this codebase, that is what it is holding: a rotation plus a translation, with methods to compose (@), invert (.inverse()), and interpolate.

The 4×4 trick

Carrying R and t separately is annoying, because composing two transforms means R₂(R₁p + t₁) + t₂ — messy. So they are glued into one 4×4 matrix:

      ⎡ R₁₁ R₁₂ R₁₃  tx ⎤
  T = ⎢ R₂₁ R₂₂ R₂₃  ty ⎥       and points become  ⎡X Y Z 1⎤ᵀ
      ⎢ R₃₁ R₃₂ R₃₃  tz ⎥
      ⎣  0   0   0    1 ⎦

With that padding, T · p gives exactly Rp + t, and composing transforms becomes plain matrix multiplication. This is why every pose in transforms.json is a 4×4 nested list, and why the code slices T[:3,:3] for the rotation and T[:3,3:] for the translation:

# utils/point_utils.py — project()
rot = T_w2c[:3, :3]
t   = T_w2c[:3, 3:]
point3d_cam = rot @ pts + t

Direction matters, and it is the #1 source of bugs

A transform has a direction, encoded in the name. This repository uses a consistent and readable convention:

Reading transform names

T_world_camera means “transform from camera coordinates to world coordinates.” Read the subscripts right to left: source on the right, target on the left. This is also called a camera-to-world matrix, abbreviated c2w.

Its inverse, w2c, goes the other way: given a point in world coordinates, it tells you where that point sits relative to the camera.

The mnemonic that makes them stick: the translation column of a c2w matrix is the camera's position in the world. That is genuinely useful — c2w[:3, 3] is where the glasses were. The translation column of a w2c matrix is not the camera position and means nothing intuitive on its own.

Which one you need depends on the question:

  • “Where was the camera when this frame was shot?” → c2w. This is what transform_matrix stores in every JSON frame.
  • “Where does this world point land in the image?” → w2c, then K, then divide. Projection always needs w2c.

Which is exactly why every projection site in this codebase starts by inverting:

# extract_aria_vrs.py
c2w = np.array(frame["transform_matrix"])
w2c = np.linalg.inv(c2w)

Composing the chain

Here is the piece that makes the whole pipeline work. SLAM tells you where the device is in the world. Factory calibration tells you where each camera sits on the device. Neither alone tells you where the camera is in the world — but composed, they do:

# extract_aria_vrs.py — to_aria_image_frame()
t_world_camera_read_center = (
    pose_info.transform_world_device
    @ camera_calib.get_transform_device_camera()
)

Read that right to left: start in camera coordinates, hop to device coordinates, hop to world coordinates. The result is the camera's pose in the world, and it is written into transforms.json as transform_matrix for every single frame. That one line is the heart of preprocessing.

Why matrix order looks backwards

A @ B applied to a point means “do B first, then A.” Composition reads right to left because that is the order the point actually passes through them. Once you internalise this, T_world_device @ T_device_camera reads naturally: the inner subscripts (device) cancel, leaving T_world_camera.

The convention that saves this repository a headache

Different systems disagree about which way the axes point. OpenGL cameras look down −Z with Y up. Blender uses Z-up. COLMAP — the structure-from-motion tool that 3D Gaussian Splatting was built around — uses X-right, Y-down, Z-forward.

Aria uses X-right, Y-down, Z-forward too. They match exactly, which is why you will find this comment in the code and no conversion anywhere:

# Gaussian Splatting (COLMAP) use the same coordinate system as Aria
# Therefore there is no coordinate system conversion needed.
Where this stops being true

The moment you export the trained PLY to a tool with a different convention — Isaac Sim, Unity, most game engines — a conversion is needed, and nothing in this repository will do it for you. If your splat comes out upside-down or mirrored in a downstream tool, this is the first thing to check.

Check yourself

You have T_world_camera. How do you get the camera's position in the world?

Take the translation column: T[:3, 3]. No inversion, no multiplication. This works only because it is a camera-to-world matrix — the same slice of a w2c matrix is not a position.

Why does the code invert transform_matrix before projecting points?

transform_matrix is c2w, but projection needs points expressed relative to the camera, which is what w2c produces. So w2c = inv(c2w), then p_cam = R·p_world + t, then K, then divide by z.

Gen 2 has four SLAM cameras. How many T_device_camera matrices exist, and how often do they change?

Five — one per camera including RGB. They are almost fixed (the glasses are rigid) but MPS re-estimates them over the recording because the frame flexes slightly with temperature and wear. That estimate is what online_calibration.jsonl holds, and it is why the code looks up the nearest in time calibration rather than using a single constant.

Chapter 3 / Part I · Seeing / 40 min

Real lenses lie: distortion and rectification

The pinhole model is a fiction. Actual lenses bend light in ways that break it — especially the extremely wide ones on Aria. This chapter explains what “rectified”, “resampling”, and “upsampling” mean, because those three words are where most people get lost.

Why straight lines come out curved

A pinhole has no lens, so it obeys u = f·X/Z exactly — but it also admits almost no light, so real cameras use glass. Glass refracts, and no practical lens refracts perfectly. The wider the field of view, the worse it gets.

The visible symptom is that straight lines in the world become curved in the image. Aria's RGB camera covers roughly 133° horizontally. That is a fisheye. The doorframe you walked past is a banana in the raw frame.

There is also a hard mathematical wall. Look back at FOV = 2·atan((W/2)/f): as the FOV approaches 180°, the required image width approaches infinity. A pinhole image cannot represent a 180° view, and gets absurdly inefficient well before that. At 133°, a pinhole would need to be enormous and would waste most of its pixels on the stretched-out corners. So a wide camera must use a different projection model.

The distortion model

Lens distortion is described by a handful of correction coefficients on top of the ideal projection. Aria uses a model called FISHEYE624, and you will see that string throughout the code and JSON.

Definition · FISHEYE624

A 15-parameter camera model. The name encodes its structure: 6 radial distortion terms, 2 tangential, 4 thin-prism. The full parameter vector is

[f, cu, cv, k0…k5, p0, p1, s0…s3]

The first three are focal length and principal point — the familiar ones. The remaining twelve are the distortion coefficients, and they are what the repository stores as distortion_params in each frame (a slice [3:15] of that vector).

Radial terms model how much a point gets pushed toward or away from the image centre as a function of how far out it is — this is the dominant fisheye effect. Tangential terms model the lens element not being perfectly parallel to the sensor. Thin-prism terms mop up remaining asymmetries. You never need to implement these; projectaria_tools does. You need to know they exist and that they are per-camera measured values, not constants.

What “rectify” means

Definition · rectification / undistortion

Rectifying an image means generating a new image that shows the same scene as if it had been photographed by an ideal pinhole camera. Straight lines in the world come out straight. The words undistort and rectify are used interchangeably here; the repository's function is literally called undistort_image().

Here is how it actually works, and the direction surprises people. You do not take each source pixel and figure out where it should go. You go backwards:

  1. Create the empty output image at the size you asked for.
  2. For each output pixel (u', v'), use the ideal pinhole model to work out which 3D direction that pixel represents.
  3. Feed that direction through the real FISHEYE624 model to find where it landed in the source image — some fractional coordinate like (1043.7, 812.2).
  4. Read the colour there and write it to the output pixel.

Going backwards guarantees every output pixel gets filled. Going forwards would leave holes.

Resampling, upsampling, downsampling

Step 3 produces a fractional coordinate. There is no pixel at (1043.7, 812.2) — pixels live at integers. So the value has to be estimated from the four surrounding pixels by weighted average. That estimation is interpolation, and doing it across a whole image is resampling.

Definition · the three words

Resampling — rebuilding an image on a new pixel grid by interpolating the old one. Every rectification is a resampling.

Downsampling — the new grid is coarser than the old. You are averaging away information you had. Lossy but honest.

Upsampling — the new grid is finer than the old. You are inventing pixels between real ones. It cannot add detail that was never captured; it just makes a bigger, smoother, blurrier file.

The trap this repository sets for you

The shipped Gen 2 script defaults to --rectified_rgb_focal 1280 --rectified_rgb_size 1920, giving a 2560×1920 output. Those numbers were derived for profile8, whose sensor delivers 2560×1920.

If your recording is profile10 — 2016×1512 — those same flags upsample every frame to 2560×1920. You pay 30% more disk, 30% more training memory, and 30% more time per iteration, for exactly zero additional information. Nothing errors. Nothing warns you. The splat just costs more and looks no better.

The fix is to match the output height to the sensor and scale the focal by the same ratio: --rectified_rgb_focal 1008 --rectified_rgb_size 1512 keeps the identical 90° FOV at native sampling.

Choosing your rectification parameters

Two flags, decided together. --rectified_rgb_size is the output height; the width is derived from the source aspect ratio, in one line inside process_frame:

# scripts/aria_utils.py — process_frame()
if rectified_w is None:
    rectified_w = int((rectified_h / frame.h) * frame.w)

So for a 4:3 sensor, height 1512 → width 2016. Then choose the focal to get the FOV you want at that width. A working procedure:

  1. Set height = the sensor's native height. No upsampling, no throwing away detail.
  2. Compute the resulting width from the aspect ratio.
  3. Pick the focal from f = (W/2) / tan(FOV/2) for whatever FOV you want. 90° is a sane default and matches what Gen 1's defaults effectively produced.
What happens if you go too wide

Push the FOV past what the lens actually saw and the output develops black corners — output pixels whose backward-mapped direction falls outside the source image entirely, so there is nothing to sample. undistort_image zeroes those. A modest amount is harmless (that is partly what mask.png is for), but a lot means you are training on invented black regions.

The other option: staying fisheye

The flag --extract_fisheye outputs an equidistant fisheye projection instead of a pinhole one. Equidistant means the distance from the image centre is directly proportional to the angle from the optical axis — a well-behaved model that can represent very wide views without exploding. The rasterizer supports it (camera_model="fisheye" is passed through to gsplat).

It is not the default, and for a first run you should not use it: fewer downstream tools understand it, and the rest of the pipeline is tuned around "linear". But it is the right answer if you genuinely need the full 133°.

Check yourself

Your recording is 2560×1920. You pass --rectified_rgb_size 1512. What happened?

You downsampled to 2016×1512. That is a legitimate choice — smaller files, faster training, less fine detail. Not a bug, unlike the reverse. But you must also scale the focal by 1512/1920 to keep the same FOV, otherwise you have narrowed the view as well as shrunk the image.

Why does rectification map from output to input rather than input to output?

So every output pixel is guaranteed a value. Mapping forwards, several source pixels can pile onto one destination while other destinations get nothing — you would have to fill holes afterwards. Backward mapping plus interpolation avoids the problem entirely.

What does “90° horizontal FOV” actually cost you, given the lens sees 133°?

You are cropping away the outer ~43° of what the camera captured. Those pixels are discarded before training ever sees them, which reduces scene coverage per frame — a real cost, offset by the fact that a pinhole at 133° would be impractically large and mostly stretched. The equidistant fisheye output is the escape hatch if that crop hurts you.

Time is a coordinate

A moving camera's pose is a function of time, and a rolling-shutter frame doesn't have a single time. Getting this wrong biases every pose in the dataset by a fixed amount — invisibly.

Nanoseconds, and why

All Aria timestamps are integer nanoseconds (10⁻⁹ s) since device boot. Not epoch time, not seconds. The reason for the resolution: at a brisk walk you cover about 1.4 m/s, so 1 ms of timing error is 1.4 mm of position error, and at 3 m distance that is already a visible fraction of a pixel. Microseconds would be adequate; nanoseconds are free.

You will see three units in the code and mixing them up is a genuine hazard:

ns
Image capture timestamps, trajectory timestamps, everything in transforms.json. Integers.
µs
The MPS semi-dense observation table's frame_tracking_timestamp_us column. This is why you see frame["timestamp"] / 1e3 before joining.
s
Exposure duration (exposure_duration_s) and readout time as reported by MPS (ReadoutTimesSec). Floats.

Global shutter vs rolling shutter

A global shutter sensor exposes every pixel simultaneously, then reads them all out. One frame, one instant, one pose. Clean.

A rolling shutter sensor exposes and reads out one row at a time, top to bottom. The last row's exposure begins milliseconds after the first row's. If the camera moved during that sweep — and on head-mounted glasses it always did — different rows of the same image were taken from different places.

Definition · readout time

The interval from the first pixel being read to the last pixel being read, for one frame. projectaria_tools documents it exactly that way. On the reference Gen 2 recording it is 10.10 ms for RGB and 0.00 ms for every SLAM camera.

Which instant does the timestamp mean?

Here is the subtle part. Each image record carries one capture_timestamp_ns. Given that the frame spans 10 ms, what does that number point at — the start of readout, or the middle?

Aria documents it as the centre of exposure of the middle row. The Gen 2 MPS point-cloud spec likewise defines its frame timestamps as “center of exposure.” The original upstream repository treated it as the start of readout. That is a half-readout bias applied to every pose in the dataset:

ConfigurationReadoutBias if misreadPosition error @ 1.4 m/s
Gen 1 RGB, full res16 ms8 ms~11 mm
Gen 2 RGB, profile838 ms19 ms~27 mm
Gen 2 RGB, profile1010.1 ms5.05 ms~7 mm

A systematic 27 mm offset on every camera in the dataset is not noise that averages out — it is a consistent lie that the optimiser will happily bake into the geometry. The port fixes the default and keeps the old behaviour available behind --timestamp_convention readout_start so you can A/B against published results.

The three timestamps get derived like this:

# extract_aria_vrs.py — to_aria_image_frame()
if timestamp_convention == "center":
    capture_time_middle = image_record.capture_timestamp_ns
    capture_time_start  = int(round(capture_time_middle - half_readout_ns))
    capture_time_end    = int(round(capture_time_middle + half_readout_ns))

Each frame therefore ends up with three poses — at read start, read centre, and read end — so that a renderer can model the sweep. Chapter 21 shows how training uses them.

Interpolating a pose

SLAM gives poses on a 1 kHz grid: one every millisecond. Your frame's timestamp will essentially never fall exactly on that grid. So the pose has to be interpolated between the two bracketing samples.

Interpolating the translation is easy — it is a straight weighted average. Interpolating the rotation is not: averaging two rotation matrices element-wise produces something that is no longer a rotation matrix. The correct operation walks along the shortest arc in rotation space, and sophus.interpolate does it:

# scripts/aria_utils.py — interpolate_closeloop_trajectory_pose()
ratio = (time_ns - start_time) / (end_time - start_time)
interp_pose_SE3 = interpolate(
    start_pose.transform_world_device,
    end_pose.transform_world_device,
    ratio,
)

The lookup that finds the bracketing pair is a binary search (bisection_timestamp_search) over a sorted array — O(log n) against 155,000 poses. If the requested time falls outside the trajectory entirely, the function returns None and the caller drops the frame. That is the mechanism behind “fewer output frames than the VRS contains”: the trajectory starts after tracking initialises, so the first second or so of video has no pose and is discarded.

Exposure and gain

Two more per-frame numbers ride along, and both matter later:

exposure_duration_s
How long the shutter was open. Longer = brighter, and more motion blur. Auto-exposure changes this constantly as you walk from shade into sun.
gain
Analog amplification applied after capture. Higher = brighter and noisier.

Their product is the frame's total brightness multiplier. Because auto-exposure varies it frame to frame, two images of the identical wall can have very different pixel values. Chapter 22 explains how the model divides this out so the Gaussians learn scene radiance rather than camera settings.

Motion blur is not recoverable

Rolling shutter can be modelled. Motion blur — the smear from the scene moving during a single row's exposure — mostly cannot. Gen 2 has no exposure-capped recording profile equivalent to Gen 1's Profile 31, so if you want short exposures you need a custom profile with fixed_exposure. This is a capture-time decision that no flag can undo afterwards.

Check yourself

Your SLAM camera reports a readout time of 0.0 ms. Is the data broken?

No — it is correct. All Aria SLAM cameras are global shutter, so there is no rolling readout to report. MPS omits the field, get_readout_time_ns sees None, and returns 0.0. The three derived timestamps then collapse to the same value, which is exactly right for a global-shutter frame.

Why can't you look up readout time from a table keyed on image height?

Because the same output resolution can come from different sensor modes. Gen 2 profile8 delivers 2560×1920 by reading out the full 4032×3024 sensor and downscaling in the ISP — 38 ms — while a binned mode at the same output size would be far faster. The only reliable source is what the recording itself reports, which arrives in online_calibration.jsonl. That is also why profile10 works despite its readout being undocumented.

Your 4,719-frame recording produces 4,676 output frames. Bug?

No. The MPS trajectory covers a slightly shorter window than the video — it starts after SLAM initialises and ends before the recording does. Frames outside that window return None from pose interpolation and are dropped. A ~1% loss at the ends is normal and worth stating explicitly in any write-up.

What a 3D Gaussian is

The scene is represented as a few million translucent, coloured, oriented blobs. Each one is described by about 60 numbers, and every one of those numbers is learned by gradient descent.

The representation problem

You have a few thousand photographs of a room. You want to render the room from a viewpoint you never photographed. What data structure holds the room?

A mesh is the classical answer, but meshes are painful to optimise — you have to decide the topology up front, and gradient descent cannot easily add or remove triangles. Neural radiance fields (NeRF) put the scene in the weights of a small network, which optimises beautifully but renders slowly, because every pixel requires marching a ray through dozens of network evaluations.

3D Gaussian Splatting takes a third route: represent the scene as an unstructured cloud of translucent ellipsoidal blobs. It optimises well (every parameter is continuous and differentiable), it renders fast (blobs project to 2D shapes and get blended, no ray marching), and the number of blobs can grow and shrink during training.

Anatomy of one Gaussian

A single Gaussian in this codebase is a bundle of parameters, all of them optimised. You can read them straight out of create_splats_with_optimizers in model/vanilla_gsplat.py:

means · [N,3]
Where the blob is, in world coordinates. Initialised from the MPS semi-dense point cloud.
scales · [N,3]
How big it is along each of its three local axes. Stored as a logarithm so the optimiser can never drive a size negative — the real scale is exp(scales).
quats · [N,4]
Its orientation, as a quaternion. Four numbers describing a rotation, normalised internally by the rasterizer.
opacities · [N]
How solid it is. Stored as a logit, so the real opacity is sigmoid(opacities), guaranteed to land in (0, 1).
rgb_sh0 · [N,1,3]
Base colour, in spherical-harmonic form. This is the colour seen from any direction.
rgb_shN · [N,15,3]
View-dependent colour terms. These let a blob look different from different angles — specular highlights, glossy reflections.
Why scales and opacity are stored transformed

Gradient descent will happily propose a negative scale or an opacity of 3.7. Rather than clamping (which kills the gradient), the parameters live in an unconstrained space and get squeezed into the valid range by an activation on every use. scales lives in log space; opacities lives in logit space. In the repository these are exposed as activated_scales and activated_opacities, and the raw values are what the optimiser touches.

Mean plus covariance

Mathematically a 3D Gaussian is a bell curve in three dimensions: a centre (the mean) and a 3×3 covariance matrix describing how it spreads. The covariance is not stored directly — 9 numbers with awkward constraints — but factorised as rotation × scale:

Σ = R · S · Sᵀ · Rᵀ        where S = diag(exp(scales)), R = from quats

which is guaranteed to be a valid covariance for any value the optimiser proposes. The geometric picture: a unit sphere, stretched by scales along three axes, then rotated by quats, then placed at means. An ellipsoid whose density fades smoothly outward rather than having a hard edge.

Spherical harmonics, plainly

A real surface does not look the same from every angle. A varnished table is bright from one side and dull from another. To capture that, each Gaussian's colour is a function of viewing direction rather than a fixed RGB triple.

Spherical harmonics (SH) are the standard basis for such functions — think of them as a Fourier series on the surface of a sphere. Degree 0 is a constant (same colour everywhere). Degree 1 adds a smooth left/right, up/down, front/back variation. Each higher degree adds finer angular detail.

DegreeCoefficientsPer Gaussian (RGB)Captures

At the configured sh_degree: 3, each Gaussian carries 48 colour numbers plus 3 for position, 3 scale, 4 rotation, 1 opacity — 59 parameters. Multiply by a couple of million Gaussians and you can see why this is a GPU job.

The degree schedule

Training does not start at degree 3. sh_degree_interval: 1000 means a new degree is unlocked every 1000 iterations, so the model learns flat colours first and only later gains the freedom to fake view-dependence. Letting all degrees loose from step one lets the model explain away geometry errors as weird lighting — a classic failure mode.

What “splat” means

The word comes from the rendering step. Each 3D ellipsoid is projected to the image plane, where it becomes a 2D ellipse with a soft falloff — a splat of paint. The image is built by compositing millions of these overlapping splats in depth order. Chapter 6 covers exactly how.

Check yourself

Why is scales stored as a logarithm?

So the optimiser works in an unconstrained space. Any real number is a valid scales value, and exp() maps it to a strictly positive size. Clamping at zero instead would produce zero gradient for any Gaussian that hit the floor, and it would be stuck there forever.

A Gaussian's rgb_shN coefficients are all zero. What does it look like?

Exactly the same colour from every direction — perfectly matte. That is also how every Gaussian starts, since colors is initialised to zeros with only the degree-0 term filled in from the point cloud colour.

Why not store the 3×3 covariance matrix directly?

Because gradient descent would quickly propose a matrix that is not a valid covariance (not symmetric, or not positive-definite), and the render would be undefined. Factorising as R·S·Sᵀ·Rᵀ means every proposal the optimiser can make yields a valid ellipsoid.

How a splat becomes a picture

Projection, sorting, alpha compositing — then the whole thing runs backwards to produce gradients. Plus the trick that lets the cloud grow where it needs detail.

The forward pass, in five steps

  1. Cull. Transform every Gaussian's centre into camera space with w2c. Discard anything behind the camera or outside the frustum. This is Chapter 2's maths at scale, millions of points at once.
  2. Project. Each surviving 3D ellipsoid becomes a 2D ellipse on the image plane. The centre projects with K and the perspective divide; the covariance projects through a local linear approximation of the projection.
  3. Evaluate colour. Compute the view direction from camera to Gaussian, evaluate the spherical harmonics along it, get an RGB value for this particular view.
  4. Sort. Order every splat by depth, back to front (in practice, tile by tile).
  5. Composite. Blend them in order.
Definition · alpha compositing

Walking front to back, each splat contributes some colour and absorbs some of what is behind it. Track a running transmittance T (how much light still gets through), starting at 1:

C += T · αᵢ · colourᵢ
T *= (1 − αᵢ)

where αᵢ is the splat's opacity scaled by its Gaussian falloff at that pixel. Once T is near zero, everything further back is invisible and the loop stops early. The final 1 − T is the pixel's alpha, which the code returns as render_alphas.

Depth is produced the same way — instead of accumulating colour, accumulate each splat's depth weighted by its contribution. That is what render_mode="RGB+ED" requests from gsplat: RGB plus expected depth, in one pass. The repository reads it out as the fourth channel:

# model/vanilla_gsplat.py — forward()
image  = einops.rearrange(render_colors[..., :3], "b h w c -> b c h w")
alphas = einops.rearrange(render_alphas,          "b h w c -> b c h w")
depth  = render_colors[..., 3]  # (B, H, W)

Why this is fast

Nothing here is a ray march. Every Gaussian touches the pixels it covers and no others, and the whole thing is a sort plus a blend — operations GPUs are built for. The image is diced into 16×16 tiles, each Gaussian is assigned to the tiles it overlaps, and each tile is blended independently by its own block of threads. A scene renders in milliseconds rather than seconds.

Why this is differentiable

Every step above is a smooth function of the parameters. Nudge a Gaussian's position and the rendered pixels change smoothly. Nudge its opacity and they change smoothly. So you can define an error between the render and the real photograph, and backpropagate that error all the way to means, scales, quats, opacities, and every SH coefficient.

The Gaussian falloff is what makes this work. A hard-edged ellipse would have zero gradient in its interior and an undefined one at the boundary; a soft falloff gives every pixel a meaningful opinion about where the blob should move.

The training loop

The whole of training is this, thirty thousand times:

Densification: the part that makes it work

Starting from a fixed set of Gaussians would fail. Regions the initial point cloud missed would stay empty; regions with fine detail would be represented by blobs too coarse to capture it. So the cloud is adaptive — Gaussians get added and removed as training proceeds.

The signal is the gradient of the loss with respect to each Gaussian's screen-space position. A large gradient means “this blob is being pulled hard in the image; it is failing to explain what it covers.” Two responses, chosen by size:

clone
Blob is small and under strain → duplicate it. Under-reconstruction: not enough coverage. Threshold: grow_scale3d: 0.01.
split
Blob is large and under strain → replace with two smaller ones. Over-reconstruction: one blob is trying to cover detail it cannot resolve.
prune
Opacity below prune_opa: 0.005, or scale above prune_scale3d: 0.1 → delete. Cleans up invisible and bloated blobs.
reset
Every reset_every: 3000 steps, opacities are knocked back down. Floaters that survived only by being faint get culled on the way back up.

All four run between iteration refine_start_iter: 500 and refine_stop_iter: 15000, every refine_every: 100 steps. After 15,000 the topology is frozen and the remaining half of training just polishes parameters. Every one of those numbers is in conf/opt/simple_gsplat_30K.yaml and is yours to change.

The other strategy

densification_strategy: MCMC swaps clone/split/prune for a Markov-chain formulation that maintains a fixed Gaussian budget (cap_max: 6,000,000) and adds noise to escape local minima. It is often more robust on sparse captures, and it lets you cap memory precisely. The default is fine for a first run; MCMC is the knob to reach for if the default cloud explodes or starves.

Check yourself

Why sort the splats at all?

Because alpha compositing is order-dependent. A red splat in front of a blue one gives a different pixel than blue in front of red. Sorting by depth is what makes “in front of” meaningful.

What does a high screen-space position gradient tell you about a Gaussian?

That moving it in the image would reduce the loss a lot — the region it covers is badly explained. The densifier reads this as “more capacity needed here” and either clones or splits the blob depending on its size.

Why freeze densification at iteration 15,000 out of 30,000?

Adding and removing Gaussians disturbs the optimiser's state — every new blob starts with fresh Adam moments. Freezing the structure lets the second half converge cleanly on a stable set. It also bounds the final model size, which matters for export.

Why egocentric capture is hard

Every extra mechanism in this repository is compensating for one of those.

The failure modes, in advance

Knowing what the algorithm demands tells you exactly how it will fail:

  • You rotated in place instead of walking. No baseline → no parallax → depth unobservable. The splat looks fine from the capture position and collapses the moment you move the virtual camera.
  • Trees, and it was windy. Static-scene assumption violated. Foliage smears. Not a bug in the port.
  • Sparse depth came out empty. One supervision signal silently absent. Geometry drifts in low-texture regions. This one is invisible unless you read the match-rate line the code prints — see Chapter 15.
  • Poses biased by half a readout. Everything is consistently slightly wrong, so the optimiser finds a consistent slightly-wrong geometry. The render looks plausible and measures worse than it should.

Check yourself

Why can't the rasterizer just take the raw fisheye images?

Because it projects a 3D Gaussian's covariance to 2D through a local linear approximation of the camera projection. Under heavy fisheye distortion that approximation breaks down, especially away from the centre. gsplat does support an equidistant fisheye model — which is what --extract_fisheye targets — but not the full FISHEYE624 with all its distortion coefficients.

What would happen if you initialised from random points instead of MPS points?

It usually still converges, but slowly and to a worse optimum — you would need far more densification steps to discover the scene's structure from scratch. The config supports it (init_type with init_num_pts: 100_000), but with a real point cloud available there is no reason to.

What MPS actually does

MPS runs SLAM — Simultaneous Localisation and Mapping — over your recording. It tracks visual features across the SLAM camera streams, fuses them with the IMU, and solves jointly for two unknowns: where the device was at every instant, and where the 3D points it saw are located. Then it runs bundle adjustment, a global optimisation that refines everything at once to minimise total reprojection error.

You submit it and wait:

aria_mps single -i "my_recording.vrs" --features SLAM

Roughly thirty minutes for a few-minute recording. The result is a folder mps_<name>_vrs/slam/.

File 1 — closed_loop_trajectory.csv

~50 MB. Where the device was, 1000 times per second. Each row is a timestamp plus T_world_device, plus linear and angular velocity and a quality score.

Closed loop vs open loop

MPS emits two trajectories. Open loop is the real-time estimate — it drifts, because small errors accumulate with no way to correct them. Closed loop has had loop closure applied: when the system recognises a place it has been before, it corrects the entire trajectory backwards to make the two visits agree.

Closed loop is globally consistent and is the only one this pipeline uses. open_loop_trajectory.csv is ignored entirely. This is also why Chapter 25 tells you to revisit viewpoints — loop closure needs something to close on.

The file is read once at the top of run_single_sequence and interpolated at every frame timestamp thereafter. It is also symlinked into the rectified output folder, because training reads it again to interpolate rolling-shutter sub-poses.

File 2 — online_calibration.jsonl

~9 MB. One JSON object per line, roughly 1,500 records. Each holds the estimated intrinsics and extrinsics of every camera at that moment, plus — critically — the readout times.

“Online” means re-estimated during the recording rather than taken from the factory. Glasses flex; temperature shifts things by micrometres; over a 2-metre baseline that is a real reprojection error. MPS tracks it.

The port's most consequential discovery lives here:

# scripts/aria_utils.py — get_readout_time_ns()
for online_calib in online_camera_calibs:
    for camera_calib in online_calib.camera_calibs:
        if camera_calib.get_label() != camera_label:
            continue
        readout_sec = camera_calib.get_readout_time_sec()
        # None => global shutter. Constant across a recording, so the first
        # record that mentions this camera is authoritative.
        return 0.0 if readout_sec is None else float(readout_sec) * 1e9

The upstream repository looked readout time up in a table keyed on image height, hardcoding Gen 1's 2880/1408/480 resolutions. Reading it from MPS instead makes the whole pipeline profile-agnostic — profile8, profile10, and any custom profile self-describe, and no table ever needs maintaining. It is also the only way profile10 can work at all, since its readout time is not publicly documented.

File 3 — semidense_points.csv.gz

~109 MB compressed. The 3D point cloud. Each point carries a unique id (uid), a world position, and two uncertainty measures: distance_std and inverse_distance_std.

“Semi-dense” sits between sparse (a few thousand corner features) and dense (every pixel). MPS tracks points along edges and textured regions — enough to outline the scene's structure, not enough to be a surface.

This file does two separate jobs, and confusing them causes confusion later:

  • It is the initialisation for the Gaussians. Every point becomes a Gaussian at step zero.
  • It is the source of depth values for the sparse depth maps.

Nanoseconds, centre of exposure. Also the image filename, which is how the two get matched. And, divided by 1000, the key used to join against the MPS observation table.

Check yourself

How do you read a frame's readout time out of the JSON?

timestamp_read_end − timestamp_read_start, in nanoseconds. There is no explicit field. Training does exactly this when constructing an AriaCamera: readout_time_ns=frame["timestamp_read_end"] - frame["timestamp_read_start"].

You open a transforms.json and distortion_params is present. Which stage produced it?

Stage 1 — this is a raw, pre-rectification file. Rectified files have no distortion parameters, because the whole point of rectification is that the ideal pinhole model needs none.

Why is cx equal to (w−1)/2 rather than w/2?

Pixel centres are at integer coordinates 0 … w−1, so the geometric centre of the grid sits at (w−1)/2. For a 2016-wide image that is 1007.5, not 1008. A half-pixel offset sounds negligible until you accumulate it across a reprojection chain.

Check yourself

Why resolve readout time outside the per-frame closure?

It is constant for a camera across a recording, and the lookup scans the online-calibration list. Doing it 4,719 times would be pure waste. The same reasoning applies to device_calib, which the port also hoisted out of the loop.

A frame is dropped. Which of the three interpolations failed?

You cannot tell from the output — all three return the same None. In practice it is nearly always the first or last frames of the recording, where the trajectory does not yet or no longer cover the requested time. Frames near the start fail on read_start first, since that is the earliest of the three.

Why does the pose composition use the online calibration rather than factory?

Because the glasses flex. Online calibration re-estimates T_device_camera during the recording, absorbing thermal and mechanical drift that factory values cannot know about. --use_factory_calib exists to switch back, mainly for debugging.

undistort_image — the actual warp

# scripts/aria_utils.py
def undistort_image(frame, image_raw, camera_model, ow, oh, f):
    proj_params = np.asarray([frame.fx, frame.cx, frame.cy])
    proj_params = np.concatenate((proj_params, frame.distortion_params))

    frame_calib = calibration.CameraCalibration(
        frame.camera_name,
        calibration.CameraModelType.FISHEYE624,
        proj_params,
        SE3(),                  # identity: we only care about intrinsics here
        frame.w, frame.h,
        None, 90.0, "",
    )

    if camera_model == "linear":
        out_calib = calibration.get_linear_camera_calibration(ow, oh, f)
    elif camera_model == "spherical":
        out_calib = calibration.get_spherical_camera_calibration(ow, oh, f)

    return calibration.distort_by_calibration(image_raw, out_calib, frame_calib)

Read it as three steps. Rebuild the source camera model from the intrinsics and distortion coefficients stored in the JSON. Construct the target camera model — an ideal pinhole (linear) or equidistant fisheye (spherical) at the requested size and focal. Then hand both to distort_by_calibration, which does the backward mapping and interpolation from Chapter 3.

The identity pose

SE3() is passed as the camera's extrinsic because rectification is a purely 2D image operation — where the camera is has no bearing on how its lens distorts. The pose is carried separately in transform_matrix and is copied through unchanged.

Why they exist at all

Each of the three is a per-pixel lookup table that gets applied to every frame. Because they are constant for a camera, they are computed once and stored as images rather than recomputed per frame. Critically, they must go through the same rectification as the images — a lookup table in raw fisheye coordinates is useless against a rectified frame.

vignette.png — lens shading

Real lenses deliver less light to the corners than the centre. That radial darkening is vignetting, and it is a property of the optics, not the scene. Left uncorrected, the optimiser would try to explain it as the room genuinely being darker near the edges of every frame — which is impossible to satisfy consistently and produces mushy, incorrect radiance.

The correction is a per-pixel multiplier. Gen 1 ships measured masks for its exact sensors:

# scripts/aria_utils.py — get_rectified_vignette_image()

    vignette_path = input_root / "vignette_imx577_16bit.png"
else:
    vignette_path = input_root / "vignette_ov7251.png"

Gen 2 does not, and the port makes a deliberate choice rather than improvising one:

if generation == "Gen2":

    # Gen 1 lens-shading models for the IMX577 (RGB) and OV7251 (SLAM)
    # sensors at Gen 1 resolutions; Gen 2 uses different sensors at
    # different resolutions and aspect ratios, so applying them would
    # bake a wrong correction into the splat.
    channels = 3 if is_rgb else 1

Why all-ones is the right answer, not just the safe one

Gen 2 performs lens-shading correction on-device, in the ISP (the rgb_camera.lsc profile option). The frames that reach you have already been corrected. Applying a second correction — especially one measured on a different sensor at a different aspect ratio — would actively make things worse. A neutral vignette is arguably correct rather than merely defensive.

    # mask_imx577.png is a 1408x1408 square circular-FOV mask for the
    # Gen 1 RGB sensor. Stretching it onto Gen 2's 4:3 frame would put
    # the valid-pixel boundary in the wrong place across the whole image.
    mask_raw = np.ones((input_h, input_w)).astype(np.float32)

The reasoning at the end of that comment matters: undistort_image already zeroes pixels that fall outside the source fisheye, so the boundary that actually matters is enforced by rectification itself. A hand-drawn mask would only add a second, wrong boundary.

image_index.png — the rolling-shutter row map

The cleverest of the three, and the least obvious.

# scripts/aria_utils.py — get_rectified_row_index()
H, W = frame.h, frame.w
array = np.linspace(0, 1, H, dtype=np.float32).reshape(H, 1)

return (image_index_rectified * 255).astype(np.uint8)

Build a gradient image where every pixel's value is its row number, normalised to 0…1. Then push that gradient through the exact same rectification the real images get. The result answers a question you cannot otherwise answer:

What it encodes

“This pixel in the rectified image — which row of the original rolling-shutter sensor did it come from?”

Rectification moves pixels around. A pixel at the top of the rectified frame did not necessarily come from the top of the sensor, especially near the corners where fisheye distortion is strongest. Since the rolling shutter reads the sensor in row order, you need the sensor row, not the output row, to know when that pixel was captured.

Warping the gradient through the same transform as the images gives exactly that mapping, for free. At train time this image is quantised into a handful of time buckets and used as a torch.gather index — Chapter 21 shows the exact call.

The bug all three can cause

Size mismatch = training crash

All three PNGs must match the rectified image size exactly. If they do not, training dies in Camera.vignette_image.expand_as() with a broadcast error that says nothing about vignettes.

Gen 1's square RGB sensor hid this: forcing output_w == output_h was harmless when the source was square too. On Gen 2's 4:3 sensor, the images derive their width from the aspect ratio while a pinned-square helper does not — and they disagree. The port's fix is to not pass output_w to any of the three, letting each derive width the same way process_frame does. The call sites carry a long comment explaining precisely this.

Which is why the verification snippet in Chapter 17 checks these three sizes before you spend GPU hours.

An asymmetry worth noticing

RGB cameras get all three files. SLAM cameras get vignette and mask but no image_index.png — they are global shutter, so there is no per-row timing to encode. Training mirrors this: it only looks for the row-index image when the camera label starts with camera-rgb.

Check yourself

Why warp the row-index gradient instead of just computing rows in the output image?

Because rectification is not a row-preserving operation. Output row 40 draws from many different sensor rows depending on horizontal position, especially near the corners. Only warping the gradient captures that relationship correctly.

Your vignette.png is 1512×1512 but the images are 2016×1512. What went wrong, and what breaks?

Something forced a square output for the helper images while the real images used the source aspect ratio. Training crashes at the first expand_as — a broadcast error naming tensor shapes, not vignettes, which is why it is worth checking up front.

Why is a neutral vignette better than stretching the Gen 1 asset?

Because the Gen 1 masks measure a different sensor (IMX577) at a different resolution and aspect ratio. Stretching one onto a Gen 2 frame applies a photometric correction that is wrong at essentially every pixel — a systematic error baked into the reconstruction. And Gen 2 already corrects lens shading in the ISP, so no further correction is called for.

Stage 3 — sparse depth for SLAM

The most expensive stage, the one with the most interesting bugs, and the one that fails silently if you are not watching. Read this chapter carefully.

The goal

For each SLAM frame, produce a list of pixels with known distance. Photometric loss alone leaves geometry ambiguous on blank walls and repeating textures; these measured depths pin it down.

The recipe is a two-hop lookup:

  1. Which points did this frame see? → observations table, keyed by timestamp.
  2. Where are those points in 3D? → points table, keyed by uid.
  3. Project them into this frame with its pose and intrinsics → (u, v, z).

The timestamp join — and the bug the port fixed

Step 1 is a join between the frame list and the observation table. The original code tested exact microsecond equality. Here is the replacement, with its comment intact because the comment is the lesson:

# extract_aria_vrs.py — create_visible_depth_map()
# This used to be an exact microsecond equality test, which only worked
# because Gen 1 half-readout times happen to be whole microseconds. Any
# recording whose half-readout is not an integer number of microseconds
# would match zero rows and produce an empty sparse depth map for EVERY
# frame -- silently, with no error, quietly disabling depth supervision.
observation_timestamps_us = np.sort(
    df_observations2d["frame_tracking_timestamp_us"].unique()
)
match_tolerance_us = 16_000
Why this mattered so much

Gen 1's readout times happened to be whole microseconds, so timestamp ± half_readout landed on integer microsecond boundaries and exact matching worked — by luck. Gen 2 profile10's readout is 10.10 ms, so half is 5.05 ms = 5,050 µs… but the arithmetic runs in nanoseconds and the division introduces sub-microsecond residue. Exact matching would find zero rows for every frame.

And nothing would have crashed. Every sparse-depth file would be an empty list. Depth supervision would silently do nothing across the whole dataset, and you would discover it — maybe — weeks later, wondering why the geometry was soft.

The fix matches to the nearest observation within a tolerance. 16 ms is half a SLAM frame period at 30 Hz — generous enough to absorb any timing convention, tight enough that it can never reach a neighbouring frame:

insert_idx = np.searchsorted(observation_timestamps_us, frame_timestamp_us)
for candidate_idx in (insert_idx - 1, insert_idx):
    if not 0 <= candidate_idx < len(observation_timestamps_us):
        continue
    candidate = observation_timestamps_us[candidate_idx]
    if abs(candidate - frame_timestamp_us) <= match_tolerance_us and (
        matched_timestamp_us is None
        or abs(candidate - frame_timestamp_us) < abs(matched_timestamp_us - frame_timestamp_us)
    ):
        matched_timestamp_us = candidate

Binary search for the insertion point, check the two neighbours, keep the closer one if it is within tolerance. O(log n) per frame.

The projection, vectorised

Once the frame's uids are known, all its points are projected in one shot:

rows = np.searchsorted(all_uids, uids)
np.clip(rows, 0, all_uids.size - 1, out=rows)
resolved = all_uids[rows] == uids       # uid actually present in the map
rows = rows[resolved]
kept_uids = uids[resolved]
unresolved_uid_count += int((~resolved).sum())

u, v, z, mask = project(all_positions[rows].T, w2c, calibK, frame_h, frame_w)

This was previously a Python loop calling project() once per point — roughly 5,700 points across 6,300 matched frames per recording, which dominated preprocessing entirely. Two things make the vectorised version possible:

  • The uid→point map is flattened once into parallel numpy arrays and cached (_point_arrays, keyed on the map's identity), so it costs nothing per camera.
  • searchsorted against the sorted uid array turns dictionary lookups into an array index.

The resolved check handles observed uids that are absent from the point cloud — searchsorted would otherwise return a neighbouring row and silently attach the wrong 3D position to that observation. The count is reported at the end.

project(), and the operator-precedence bug

The projection helper in utils/point_utils.py is short, and its docstring documents two real bugs the port fixed. Both are worth studying because both are the kind you would write yourself.

# the OLD code
if (
    u_proj < 0
    or u_proj >= frame_w - 1
    or v_proj < 0
    or v_proj >= frame_h - 1 and z > 0
):
    return None, None, None, np.array([False])
Bug 1 · and binds tighter than or

That expression parses as A or B or C or (D and z>0). The depth check applies to only the last clause. A point behind the camera projects to a sign-flipped u, v that can easily land inside the image — and was accepted, and written into sparse depth with a negative depth value. Chapter 1 warned you that dividing by a negative z produces a plausible-looking pixel.

Bug 2 · the branch condition

The old code chose between scalar and batch handling with if point3d.shape[-1] > 1. A batch that happened to contain exactly one point — or zero — fell into the scalar branch and returned mask=None, which every batched caller then used as an array index. Rank distinguishes the two cases, not batch size.

The fixed version handles both uniformly:

# utils/point_utils.py — project()
single = point3d.ndim == 1
pts = point3d.reshape(3, 1) if single else point3d

point3d_cam  = T_w2c[:3, :3] @ pts + T_w2c[:3, 3:]
point3d_proj = calibK @ point3d_cam

with np.errstate(divide="ignore", invalid="ignore"):
    u_proj = point3d_proj[0] / point3d_proj[2]
    v_proj = point3d_proj[1] / point3d_proj[2]
z = point3d_proj[2]

mask = (
    (u_proj > 0) & (u_proj < frame_w)
    & (v_proj > 0) & (v_proj < frame_h)
    & (z > 0)
)

One mask, all four conditions with explicit &, including z > 0. The errstate context suppresses the division warning for points exactly on the camera plane, which the mask then rejects anyway.

The diagnostic that proves the fix

Stage 3 also counts how many points would have been wrongly accepted:

v_all = frame["fy"] * pt_cam[1] / pt_cam[2] + frame["cy"]

Check yourself

Why 16 ms tolerance and not 1 ms?

It must comfortably exceed any plausible timestamp-convention offset (up to a full readout, 38 ms on profile8 — though in practice the conventions agree at the frame level) while staying under one SLAM frame period at 30 Hz, which is 33 ms. Half a period, 16 ms, is the natural choice: generous but structurally incapable of reaching a neighbouring frame.

Your run reports 0% match for all four SLAM cameras. First thing to check?

That the observation file belongs to this recording. The join is on camera serial number and timestamp, so an MPS output from a different session produces exactly this signature — a clean 0% with no error. The code's own warning says as much.

Why did the operator-precedence bug produce plausible-looking data rather than an obvious crash?

Because a point behind the camera still divides cleanly — it just gives a sign-flipped u, v that can land inside the image bounds. The result is a well-formed entry with a negative z. Nothing errors; the depth loss just gets fed physically impossible measurements.

Stage 4 — carrying depth into RGB

The RGB camera has no depth measurements of its own. This stage borrows them from the SLAM cameras via a round trip through world space.

The problem

MPS tracks points in the SLAM camera streams only. The RGB camera appears nowhere in the observation table. Yet RGB is the camera you will train on, so RGB is where depth supervision is needed.

The solution is a two-step reprojection, and it is a clean demonstration of everything from Part I:

  1. Unproject the SLAM camera's sparse depth back to 3D world points. You know (u, v, z) and the intrinsics, so you can invert the projection.
  2. Project those world points into the RGB camera and keep whatever lands inside its frustum.

The unprojection

# extract_aria_vrs.py — fetch_visible_depth_map_for_RGB()
fx, fy = slam_frame["fx"], slam_frame["fy"]
cx, cy = slam_frame["cx"], slam_frame["cy"]
x = z * (u - cx) / fx
y = z * (v - cy) / fy

pt3d_slam  = np.stack([x, y, z])
slam_c2w   = np.asarray(slam_frame["transform_matrix"])
pt3d_world = slam_c2w[:3, :3] @ pt3d_slam + slam_c2w[:3, 3:]

This is Chapter 1's projection algebra solved for X and Y. Forward: u = fx·X/z + cx. Backward: X = z·(u − cx)/fx. Knowing z is what makes it invertible — one pixel plus one depth is one 3D point.

Then c2w lifts it from camera coordinates into world coordinates. Note the direction: this time you multiply by c2w directly, not its inverse, because you are going out of the camera frame.

The reprojection

rgb_c2w = np.asarray(frame["transform_matrix"])
rgb_w2c = np.linalg.inv(rgb_c2w)
rgb_calibK = np.array([[frame["fx"], 0, frame["cx"]],
                       [0, frame["fy"], frame["cy"]],
                       [0, 0, 1]])

u_rgb, v_rgb, z_rgb, mask = project(pt3d_world, rgb_w2c, rgb_calibK, frame["h"], frame["w"])

u_chunks.append(u_rgb)
v_chunks.append(v_rgb)
z_chunks.append(z_rgb)
inv_dist_chunks.append(inverse_distance_std[mask])
dist_std_chunks.append(distance_std[mask])
Why project() returns the mask

It returns u, v, z already filtered — but the caller has parallel arrays (the two uncertainty measures) that must be filtered identically. Returning the mask lets the caller apply the same selection to its own data. That is exactly why Chapter 15's bug — returning mask=None for single-element batches — was so damaging: callers indexed with None.

Nearest SLAM frame in time

slam_index = np.searchsorted(slam["timestamps"], rgb_timestamp)
slam_index = min(slam_index, len(slam["frames"]) - 1)
slam_frame = slam["frames"][slam_index]

Nearest rather than interpolated. The code's own comment justifies it: SLAM runs at 30 Hz, so worst-case temporal error is ~16 ms, and the depth values are approximate anyway. Interpolating sparse point sets between frames would be considerably more work for very little gain.

Check yourself

Why can you unproject a sparse depth pixel but not an arbitrary pixel?

Because unprojection needs z, and only the sparse-depth pixels have a measured one. Every other pixel is a ray with unknown depth — recovering it for all pixels is precisely what training is for.

Why multiply by slam_c2w here but by inv(rgb_c2w) a few lines later?

Directions. Going from SLAM camera coordinates to world needs c2w. Going from world to RGB camera coordinates needs w2c, which is the inverse of the RGB c2w. Same round trip, opposite ends.

Would training on the SLAM cameras be a good idea?

Rarely. They are monochrome and low-resolution, and the repository's SLAM and joint modes emit PLYs with 1 or 4 colour channels instead of 3 — which no external viewer or converter reads, including 3dgrut for NuRec/Isaac Sim export. Train RGB-only if the PLY needs to leave this repository.

Why link instead of copy

Both files are large — 109 MB of points and 50 MB of trajectory on this recording — and every rectified folder needs them. With one RGB and four SLAM cameras that is five folders, so copying would cost about 800 MB of duplicated bytes that can never disagree with each other usefully. A link costs nothing and guarantees all five folders see identical data.

Why training needs them at all

This is the part worth understanding, because it explains a design choice that looks redundant. transforms.json already contains a pose per frame — so why does training need the trajectory again?

closed_loop_trajectory.csv
Because the rectified transforms.json keeps only one pose per frame. process_frame deliberately comments out transform_matrix_read_start and _read_end. Rolling-shutter rendering needs poses between frames, at arbitrary row times, so training re-interpolates the 1 kHz trajectory itself rather than reading three precomputed poses (Chapter 21).
semidense_points.csv.gz
Because the Gaussians have to start somewhere. init_type: "sfm" seeds the cloud from these points — 4.29 M of them here, filtered by confidence — rather than from random noise. This is the file that decides where your splat begins (Chapter 19).

So the rectified folder is designed to be self-contained: hand someone that one directory and they can train, with no reference to your MPS paths or the original VRS. The symlinks are what make that true without duplicating a gigabyte.

Which means the link can break

Move, rename, or delete the MPS folder after preprocessing and both links dangle. Training then fails at load time — reading the trajectory, or reading the point cloud — with an error that names the rectified folder, not the MPS folder that actually moved. The preprocessed output looks complete, because the entries are still listed in the tree.

One Gaussian per surviving MPS point. Typically a few hundred thousand, growing to a few million through densification.

Scale, from nearest neighbours

dist2_avg = (knn(points, 4)[:, 1:] ** 2).mean(dim=-1)   # [N,]
dist_avg  = torch.sqrt(dist2_avg)
scales    = torch.log(dist_avg * init_scale).unsqueeze(-1).repeat(1, 3)  # [N, 3]
Why nearest neighbours

Each Gaussian is sized to roughly the local point spacing: knn(points, 4) finds the 4 nearest (the first being the point itself, hence [:, 1:]) and averages the distance to the other three.

The effect is adaptive resolution from step zero. Dense regions — well-textured, heavily observed — get small blobs. Sparse regions get large ones that cover their territory without leaving holes. A single global initial size would be wrong nearly everywhere.

torch.log puts it in the unconstrained space from Chapter 5, and .repeat(1, 3) makes every Gaussian start spherical. Anisotropy is learned.

Rotation and opacity

quats     = torch.rand((N, 4))                          # random orientation
opacities = torch.logit(torch.full((N,), init_opacity)) # init_opa: 0.1

Orientation is random because a sphere has no orientation to speak of — it only becomes meaningful once the scales diverge. Opacity starts low, at 0.1, which is deliberate: many overlapping faint Gaussians composite into a soft, forgiving image, and the optimiser can raise opacity where evidence supports it. Starting opaque produces hard occlusions that block gradients from reaching anything behind them.

Colour, in SH space

Only the degree-0 term is initialised; the 15 higher-order coefficients start at zero, so every Gaussian begins perfectly matte. And note the learning rates: the higher-order terms learn 20× slower. Together with the degree schedule from Chapter 5, this is a strong prior that says explain the image with geometry and base colour first; use view-dependence only as a last resort.

Three colour formats

rgb (3 channels), m (1 channel, monochrome-only training), and rgbm (4 channels, joint RGB + monochrome). The last two exist so the SLAM cameras can participate in training. Both produce PLYs with a non-standard channel count that no external viewer reads — the reason Chapter 16 says train RGB-only if the PLY has to leave this repository.

One optimiser per parameter group

Manual optimisation

Lightning normally handles zero_grad, backward, and step for you. This model does it by hand — self.manual_backward(loss) — because densification has to run between the backward pass and the optimiser step, in a specific order. That is also why training_step loops over optimisers explicitly.

The 3D smooth filter

Enabled by model.use_3d_smooth_filter: True, this is a Mip-Splatting-style anti-aliasing measure with a local twist:

# model/vanilla_gsplat.py — _apply_3d_depth_based_filter()
filter3d = torch.max(min_depth / focals * (kernel_size_3d ** 0.5), dim=0)[0]
scales_after_square = scales_square + torch.square(filter3d)
coef = torch.sqrt(det1 / det2 + 1e-7)
opacities = opacities * coef

The idea: a Gaussian smaller than one pixel at its viewing distance cannot be resolved, and rendering it produces aliasing. So enlarge it to the minimum resolvable size and reduce its opacity to compensate, preserving total contribution. The nearest observed depth (min_depth, taken from the frame's own sparse depth) sets the scale.

The comment explains the departure from Mip-Splatting: this repository uses one filter based on the camera's minimum depth rather than a per-point filter, because per-point filters can degenerate toward zero for free-viewpoint trajectories. It is also disabled at evaluation and never applied when saving the PLY, so exported opacities are the real ones.

Check yourself

Why initialise opacity at 0.1 rather than 0.9?

Low opacity keeps the early scene translucent, so gradients reach Gaussians behind others and the optimiser can sort out depth ordering. High initial opacity creates hard occlusions immediately, and whatever ends up in front — correctly or not — blocks everything behind it from learning.

Why is rgb_shN's learning rate divided by 20?

To stop view-dependent colour from becoming a dumping ground for geometry error. A model free to make a surface any colour from any angle can explain a misplaced Gaussian as an odd reflection. Slowing those terms — and unlocking degrees gradually — forces geometry to do the work first.

Why six optimisers instead of one with six parameter groups?

Densification edits optimiser state in place as Gaussians appear and disappear. Keeping each parameter's Adam moments in its own optimiser makes those edits clean; the gsplat strategy objects are written against exactly this layout.

Two layers

The model splits rendering into two functions, and knowing which is which saves confusion:

render(camera, …)
Camera-aware. Decides whether this frame needs the rolling-shutter treatment, assembles view matrices and intrinsics, and post-processes the result.
forward(intrinsics, viewmat_w2c, …)
Camera-agnostic. Takes matrices and calls the rasterizer. This is the plain nn.Module.forward, and the viewer calls it directly with arbitrary poses.

The simple path

One camera, one 4×4 world-to-camera matrix, one 3×3 K. The leading dimension C is a camera batch — gsplat can render many views of the same Gaussians in one call, which is exactly the door the rolling-shutter path walks through in Chapter 21.

Check yourself

Why does rasterization take a batch of view matrices?

So one call can render several views of the same Gaussians. Used here for the rolling-shutter sample poses (Chapter 21) — one render per time slice, then combined — and available to the viewer for multi-view rendering.

Where does camera_model="fisheye" originate?

Rolling shutter at render time

The payoff for everything in Chapter 4. Render the frame several times from several poses, then assemble the final image row-band by row-band using the map from Chapter 14.

The idea

A rolling-shutter frame was captured over ~10 ms during which the camera moved. Rendering it from a single pose is wrong for every row except the middle one. The fix:

  1. Split the readout into k time slices.
  2. Render the whole scene once per slice, from the pose at that moment.
  3. Assemble the output by taking each pixel from the slice matching its sensor row.

How many slices?

Rendering k times costs k times as much, so k is chosen per frame from how fast the camera was actually moving:

# scene/cameras.py — AriaCamera.__init__()
rs_row_quantization_range = int(
    min(
        max(readout_time / self._motion_sample_max * sampled_pixel_offset, 1),
        self._max_rolling_shutter_sample,   # 8
    )
)

Between 1 and 8. The middle term, sampled_pixel_offset, is a genuinely clever measurement:

# scene/cameras.py — _estimate_pixel_motion_offset()
uv = self.sparse_point2d
x = (u - cx) / fx * z
y = (v - cy) / fy * z

t_start = timestamp - exp_offset_ns
t_end   = timestamp + exp_offset_ns
pose_start = interpolate_aria_pose(closed_loop_traj, t_start)
pose_end   = interpolate_aria_pose(closed_loop_traj, t_end)

w2c_rel = pose_end.transform_world_device.inverse() @ pose_start.transform_world_device

u_proj, v_proj, z_proj, mask = project(pt3d, T_w2c=w2c_rel.to_matrix(), ...)
proj_offset = np.stack([(u[mask] - u_proj).abs(), (v[mask] - v_proj).abs()]).max(axis=0)
return np.percentile(proj_offset, threshold_percentile)
What it measures

“If I take this frame's sparse depth points and reproject them through the camera's motion over a 2 ms window, how many pixels do they move?” The median (50th percentile) of that displacement is the frame's motion magnitude, in the units that matter — pixels, not metres per second.

This is why the sparse depth from Stage 3–4 is needed even before the depth loss: it is the only per-frame 3D information available at camera-construction time. Frames without it fall back to a placeholder value of 1.0.

Standing still → sub-pixel motion → 1 sample → no extra cost. Whipping your head around → many pixels of motion → up to 8 samples. The budget goes where it matters.

Sampling the poses

rs_step_ns = readout_time / rs_row_quantization_range
if rs_row_quantization_range > 1:
    rs_read_start_ns = timestamp_ns - readout_time // 2
    rs_bracket_timestamps = [rs_read_start_ns + idx * rs_step_ns
                             for idx in range(rs_row_quantization_range + 1)]
    rs_sampled_timestamps = [(rs_bracket_timestamps[i] + rs_bracket_timestamps[i + 1]) / 2
                             for i in range(rs_row_quantization_range)]
else:
    rs_sampled_timestamps = [timestamp_ns]

Divide the readout into k equal brackets and take the midpoint of each — not the edges. The midpoint is the least-wrong single pose for a band of rows, in the same way that capture_timestamp_ns being the centre of exposure is the least-wrong single time for a frame.

Then each sampled time gets its own pose, interpolated fresh from the trajectory:

    pose_info = interpolate_aria_pose(closed_loop_traj, timestamp)
    c2w_SE3 = pose_info.transform_world_device @ camera2device
    w2c_array.append(c2w_SE3.inverse().to_matrix())

This is why the trajectory is symlinked into the training folder. Training does not use transform_matrix_read_start and _read_end from the JSON — it recomputes sub-poses at whatever times it decides it needs. That is also why those two fields are commented out of the rectified transforms file.

The two operations, and why they differ

Exposure samples are averaged — motion blur is a physical integration of light over the exposure window, so averaging is the correct model.

Rolling-shutter samples are gathered — each pixel came from exactly one moment, so you select rather than blend. torch.gather along dimension 0 picks, for every pixel, which of the k renders to read from.

The index comes straight from Chapter 14's row map, quantised to the number of samples actually used:

# scene/cameras.py
@property
def rolling_shutter_index_image(self):
    return torch.from_numpy(
        np.round(self._rs_row_index_image[self._camera_name]
                 * (self.rs_row_quantization_range - 1))
    ).long()

The stored PNG holds 0…1 per pixel (sensor row, normalised). Multiply by k−1 and round, and you have a valid gather index into the k renders. That is the entire payoff of warping a gradient image back in Stage 2b.

When it turns on

handle_moving_camera = camera.is_moving_camera and self.cfg.opt.handle_rolling_shutter
if is_training:
    return handle_moving_camera and self.train_iter > self.cfg.opt.handle_rolling_shutter_start_iter

Three conditions. The flag must be on (opt.handle_rolling_shutter=true), the camera must actually need more than one sample, and — during training only — the iteration must exceed handle_rolling_shutter_start_iter: 10000.

Why start late

It is up to 8× more expensive per iteration. In the first third of training the geometry is far too coarse for a few pixels of rolling-shutter correction to matter — you would be paying 8× to refine an error much smaller than the ones you already have. Turning it on at 10,000, once structure has settled, buys the accuracy where it counts. At evaluation it is always on, since correctness beats speed there.

Check yourself

Why gather rather than average the rolling-shutter renders?

Because each pixel was genuinely captured at one instant, not smeared across the readout. Averaging would invent blur that the sensor never produced. Exposure samples are averaged, because that blur is real.

Why does the pixel-motion estimate need sparse depth?

Because pixel displacement depends on distance — a nearby object sweeps across many more pixels than a distant one for the same camera motion. Without depth you cannot convert metres of camera motion into pixels of image motion, and the sample count would be a guess.

SLAM cameras are global shutter. What does this code do for them?

rs_sampled_timestamps = [timestamp_ns], rs_row_quantization_range = 1. One pose, one render, no gather. The branch is taken in AriaCamera.__init__ based on the camera name, and everything downstream falls through the single-sample path.

The problem

Walk from a shaded driveway into direct sun and auto-exposure will change the exposure time by an order of magnitude within a second. Two frames of the identical wall, taken half a second apart, will have very different pixel values.

If you compare renders to photographs directly, the optimiser has an impossible task: the same Gaussians must produce two different brightnesses for the same surface. It will compromise — and the compromise is baked-in error.

The model

The Gaussians represent irradiance — physical scene brightness, independent of camera settings. To compare against a photograph, the render is passed through a simulated camera response that applies this frame's exposure, gain and vignette. The comparison then happens in image space, where both sides have had the same treatment.

exp_all = np.array([cam.exposure_multiplier for cam in all_cam_list])
exp_median = np.median(exp_all)

for cam in all_cam_list:
    cam.radiance_weight = 1.0 / exp_median

Without this, the absolute scale of the learned radiance would depend on your camera's exposure settings — an arbitrary offset. Dividing by the median exposure across the recording anchors the radiance scale so that a typical frame lands near a multiplier of 1. Note it is a single global constant, not per-frame: the per-frame variation is handled by exposure_multiplier, while radiance_weight just sets the overall scale.

Applying it

# scene/cameras.py — expose_image_gamma()
irradiance_linear *= self.exposure_multiplier * self._radiance_weight
irradiance_gamma  *= self.exposure_multiplier * self._radiance_weight

if self.vignette_image is not None:
    v = self.vignette_image.expand_as(irradiance).to(irradiance.device)
    irradiance_linear *= v[mask_linear]
    irradiance_gamma  *= v[~mask_linear]

if self.valid_mask is not None:
    exposed_image *= self.valid_mask.to(irradiance.device)

Called once per training step, on the render, before the loss:

# model/vanilla_gsplat.py — training_step()
image = train_cam.expose_image(irradiance=renders["render"], clamp=False)
This is the expand_as that crashes

self.vignette_image.expand_as(irradiance) is the exact line that fails when vignette.png does not match the image size. The error names tensor shapes and says nothing about vignettes, which is why Chapter 14 insists you check the three PNG sizes before training.

Gamma

The function implements the sRGB transfer curve, with its two-part structure — linear near black, a power curve above:

gamma = 2.2
mask_linear = irradiance < 0.04045
irradiance_linear = irradiance[mask_linear] / 12.92
irradiance_gamma  = ((irradiance[~mask_linear] + 0.055) / 1.055) ** gamma
# ... multiply by exposure and vignette in linear space ...
irradiance_linear = 12.92 * irradiance_linear
irradiance_gamma  = 1.055 * torch.pow(irradiance_gamma, 1/gamma) - 0.055

Decode to linear, apply the multiplications there (because that is the only space where scaling light is physically meaningful), then re-encode. Doing the multiply directly on gamma-encoded values would be wrong by a nonlinear factor that varies with brightness.

Two paths, one switch

expose_image dispatches on use_nonlinear_irradiance, choosing between expose_image_gamma and expose_image_linear. The gamma path assumes the Gaussians hold gamma-encoded values and converts around the multiplication; the linear path assumes they hold linear radiance and multiplies directly.

Clamping, and its timing

image = train_cam.expose_image(irradiance=renders["render"], clamp=False)
# ...
image = image.clamp(0, 1)      # clamp radiance to the observed dynamic range
image_losses = image_loss_func(image, gt_image, ...)

Exposure is applied without clamping, then clamped just before the loss. A photograph cannot represent values outside [0, 1] — the sensor saturated — so comparing against an unclamped render would penalise the model for correctly predicting a bright sky that the camera simply could not capture.

The gain trick for rendering

def amplify_gain(self, ratio):
    self._gain *= ratio

Exposed via render.gain_amplify in the config. Since brightness is a post-hoc multiplier on stored radiance, you can brighten or darken a rendered video without retraining anything. A small demonstration that separating radiance from camera response was the right architecture.

Check yourself

Why apply exposure to the render instead of dividing it out of the photograph?

Because a photograph is clipped and quantised. Dividing a saturated white region by a large exposure value produces a wrong, unrecoverable number. Going the other direction — simulating the camera on top of the render — keeps the comparison in the space where the ground truth is actually valid.

Why do the multiplications happen in linear space?

Because doubling exposure doubles the number of photons collected, and that relationship is linear only in linear space. Gamma-encoded values are perceptually spaced; multiplying them by 2 does not correspond to twice the light.

Gen 2's vignette is all ones. Does the exposure machinery still matter?

Very much. Vignette is one of three multipliers; exposure and gain vary constantly with auto-exposure and are the dominant effect. Only the lens-shading part is neutral on Gen 2, because the ISP already did it on-device.

The photometric loss

# model/vanilla_gsplat.py — training_step()
loss = (
    self.cfg.opt.pixel_lambda * image_losses[pixel_loss_type]   # 0.8 × L1
    + 0.2 * image_losses["dssim"]                              # 0.2 × D-SSIM
)

The 3DGS standard: 80% L1, 20% D-SSIM. They measure different things, which is the point.

L1
Mean absolute per-pixel difference. Robust to outliers, but pixel-independent — it cannot tell a sharp edge from a blurred one if the average error is the same.
D-SSIM
1 − SSIM. SSIM compares local means, variances, and covariance in an 11×11 Gaussian window, so it measures structural similarity. This is the term that rewards sharpness.

The SSIM implementation is in model/loss.py — a separable Gaussian window applied via conv2d, with the standard stabilising constants C1 = 0.01² and C2 = 0.03². There is a commented-out fused_ssim import; the pure-PyTorch version is what runs.

The depth loss

Off by default (depth_loss: False), and worth understanding before you enable it:

depthloss = calculate_inverse_depth_loss(
    render_depth=renders["depth"] / self.scene_scale,
    sparse_point2d=batch["sparse_point2d"],
    sparse_inv_depth=batch["sparse_inv_depth"],
    sparse_inv_distance_std=batch["sparse_inv_distance_std"],
    losses=["huber"],
    huber_delta=0.5,
)
loss += self.cfg.opt.depth_lambda * depthloss["huber"]   # 2e-4

Three design choices, each deliberate:

  • Inverse depth. Comparing 1/z rather than z compresses far distances, so a 10 cm error at 2 m matters far more than at 50 m. That matches both measurement uncertainty and visual importance.
  • Huber, not L2. Quadratic near zero, linear beyond delta=0.5 — so a handful of badly wrong sparse points cannot dominate the gradient.
  • Uncertainty weighting. The error is divided by sparse_inv_distance_std, so points MPS was confident about count for more. The uncertainty columns carried all the way from Chapter 9 finally get used here.

The rendered depth is sampled at the sparse points with bilinear grid_sample after normalising pixel coordinates to [−1, 1] — a differentiable lookup, so gradients flow back to the Gaussians.

Two constraints

The depth loss requires batch_size == 1, and train_lightning.py asserts it (sparse point counts vary per frame, so they cannot be stacked into a rectangular batch). And depth_lambda is 2e-4 — three to four orders of magnitude below the photometric terms, because the two losses have very different natural scales. Do not raise it casually.

The step ordering

self.densification_strategy.step_pre_backward(..., info=renders["info"])
self.manual_backward(loss)
self.densification_strategy.step_post_backward(..., info=renders["info"])
for opt in self.optimizers(): opt.step()
for scheduler in self.schedulers: scheduler.step()

Strict. step_pre_backward registers which Gaussians the rasterizer touched; step_post_backward reads their accumulated gradients and decides who clones, splits, or dies. Both must straddle the backward pass, and both must precede the optimiser step so that newly created Gaussians have their optimiser state initialised before anyone tries to step them.

Evaluation

Validation runs every val_every_n_steps: 1999 and computes PSNR, SSIM and LPIPS on the held-out frames.

PSNR
Peak signal-to-noise ratio, in dB. A logarithmic transform of mean squared error. Higher is better; a 1 dB gain is meaningful, 3 dB is large. Correlates poorly with perceived quality at the top end.
SSIM
Structural similarity, 0 to 1. Closer to how humans judge similarity than PSNR.
LPIPS
Learned perceptual distance — feature distance through a pretrained network (AlexNet here). Lower is better, and it tracks human judgement best of the three.

Report all three, on the held-out split, for every run. That is what makes a result defensible rather than decorative.

The output

output/<exp_name>/
├── point_cloud/iteration_30000/point_cloud.ply    # the deliverable
├── checkpoints/                                    # every 10,000 steps
└── wandb/                                          # if enabled

The PLY holds every Gaussian's position, normals (zeros — Gaussians have no meaningful normal), SH coefficients, opacity, scale, and rotation. It carries a metadata element recording colour format, channel count, and SH degree, which load_ply reads back to reconstruct the model.

Channel count and portability

RGB training produces a standard 3-channel PLY that external viewers read. Monochrome or joint training produces 1 or 4 f_dc_* channels, which nothing outside this repository understands — including 3dgrut, the usual route to NuRec and Isaac Sim. If the PLY has to leave, train RGB-only.

Watching it run

With viewer.use_trainer_viewer=true a live viewer serves on http://0.0.0.0:8080, letting you fly around the reconstruction as it converges. It is the fastest way to spot a problem — floaters, a collapsed region, a wrong scale — long before the metrics tell you. It does cost throughput; turn it off for a production run.

Check yourself

Why is depth_lambda only 2e-4?

Because the depth term is computed on inverse depths and divided by per-point uncertainties, so its natural magnitude is enormous compared with a per-pixel L1 in [0,1]. The small weight balances the two. It is a scale correction, not a statement that depth barely matters.

Why must densification straddle the backward pass?

Its decision signal is the accumulated screen-space gradient per Gaussian, which does not exist until backward has run. step_pre_backward records who was visible; step_post_backward reads the resulting gradients. Both have to happen before the optimiser step so new Gaussians get valid optimiser state.

You want a PLY for Isaac Sim. Which settings?

RGB-only training (camera.camera_name="rgb", which is the default), giving a standard 3-channel PLY. Then a coordinate-convention conversion on the way out, since Chapter 2's Aria/COLMAP match does not extend to engine conventions.

Every Gen 2 change, and why

Nine changes across two files. Three are hardware differences, three are latent bugs Gen 2 exposed, two are correctness fixes, and one is performance. Here they are with the reasoning that justifies each.

The organising principle

Gen 1 had properties the original code quietly relied on without stating: two SLAM cameras with fixed names, a square RGB sensor, tabulatable readout times, and half-readouts that landed on whole microseconds. Gen 2 broke all four. Most of the port is removing assumptions, not adding special cases — which is why the result runs both generations from one code path.

Group 1 — hardware differences

1 · Camera labels resolved from the device

Was: camera-slam-left and camera-slam-right hardcoded throughout.
Now: get_camera_labels() intersects a per-generation candidate list with the device's actual label list.

Consequences ripple outward. fetch_visible_depth_map_for_RGB was rewritten to loop over a dictionary of arbitrary size instead of a left/right pair. is_slam_camera_label() was added so training can normalise four distinct labels down to the canonical camera-slam that downstream substring tests expect. And stream IDs are deliberately never used, since they are reassigned between generations.

2 · Readout time from MPS, not a table

Was: a lookup keyed on image height, hardcoding Gen 1's 2880/1408/480.
Now: get_readout_time_ns() reads ReadoutTimesSec from online calibration.

The docstring records why it cannot come from the device: factory calibration has no such field, and get_readout_time_sec() returns None there for every camera on both generations. Reading from the data makes the pipeline profile-agnostic — which is the only reason profile10 works, since its readout time is undocumented.

3 · Neutral vignette and full-frame mask

Was: Gen 1 lens-shading assets for the IMX577 and OV7251 sensors.
Now: all-ones vignette and full-frame mask on Gen 2.

Chapter 14's argument: the shipped assets are the wrong sensors at the wrong resolutions and aspect ratios, projectaria_tools ships no Gen 2 replacement, and Gen 2 does lens-shading correction on-device in the ISP. A null correction is arguably right, not merely safe. Stretching a Gen 1 asset would bake a wrong photometric correction into every frame.

Group 2 — assumptions Gen 2 exposed

4 · Aspect ratio, everywhere

Was: rectified output forced square.
Now: width derived from the source aspect ratio, and — critically — the same derivation applied to the three helper images.

The images were already deriving width correctly. The bug was that vignette.png, mask.png and image_index.png were being pinned square, so they disagreed with the images they multiply against. Result: a broadcast crash inside Camera.vignette_image.expand_as() at train time, with an error message that names tensor shapes and nothing else. The fix is to stop passing output_w to the three helpers, since each already derives width correctly when it is None. The call site carries a long comment saying exactly this.

5 · The timestamp join tolerance

Was: exact microsecond equality between frame timestamps and MPS observation timestamps.
Now: nearest match within 16 ms.

The most consequential fix in the port

Exact matching worked on Gen 1 only because its half-readout times happened to be whole microseconds. On any recording where that is not true — Gen 2 profile10's half-readout is 5.05 ms — zero rows match, for every frame. Sparse depth comes out empty across the entire dataset. Nothing errors, nothing warns, and depth supervision is silently a no-op.

The fix also added the match-rate print, which turned an invisible failure into a number you read on the console. That reporting is arguably as valuable as the fix itself.

6 · project() single-vs-batch dispatch

Was: if point3d.shape[-1] > 1 to distinguish a batch from a single point.
Now: single = point3d.ndim == 1.

A batch containing exactly one point — or none — fell into the scalar branch and returned mask=None, which every batched caller then used as an array index. Rank distinguishes the two cases; batch size does not. Rare on Gen 1's two cameras, much more likely on Gen 2's four, where the side cameras routinely contribute one or zero in-frustum points.

Group 3 — correctness

7 · The timestamp convention

Was: capture_timestamp_ns treated as the start of readout.
Now: treated as the centre of exposure, per Aria's documentation, with --timestamp_convention readout_start preserving the old behaviour for A/B comparison.

A half-readout bias on every pose in the dataset: 8 ms on Gen 1 full-res, 19 ms on Gen 2 profile8. At walking speed that is a systematic ~27 mm offset — not noise, and it does not average out.

8 · The project() sign bug

Was: u < 0 or u >= w-1 or v < 0 or v >= h-1 and z > 0.
Now: one explicit mask with & throughout, including z > 0.

Python's and binds tighter than or, so the depth check applied to only the last clause. Points behind the camera project to sign-flipped coordinates that can land inside the image, and were written into sparse depth with negative depth values. The port added a diagnostic that counts exactly how many such points a run would have accepted, so the impact is measured rather than assumed.

Group 4 — performance

9 · Vectorised projection, hoisted invariants, one depth pass

  • Vectorised. create_visible_depth_map called project() once per point in a Python loop — roughly 5,700 points across 6,300 matched frames. Now the semi-dense map is flattened once into cached parallel arrays (_point_arrays) and each frame projects in a single numpy call.
  • Hoisted. device_calib and readout time are resolved once per camera instead of once per frame.
  • Deduplicated. Sparse depth for the SLAM cameras used to be generated twice — once inside rectification and once in the dedicated pass, with the first result discarded. The most expensive stage of preprocessing ran twice per camera. Now it runs once, writing directly to transforms_with_sparse_depth.json, which is the file training actually consumes.

What did not change

Worth stating, because it bounds the risk:

  • The projection model. Both generations use FISHEYE624. No maths changed.
  • The coordinate convention. X-right, Y-down, Z-forward on both, matching COLMAP. No conversions anywhere.
  • The training half. Apart from label normalisation and reading readout time from the JSON, the model, losses, and rasterization path are untouched.
  • The output format. Same transforms.json schema, same PLY.

Known gaps

No Gen 2 vignette assets
None exist publicly. The neutral vignette is defensible, but a measured Gen 2 lens-shading model would be strictly better if Meta publishes one.
profile10 readout undocumented
Does not block anything — MPS reports whatever the recording used — but it cannot be independently verified against a spec.
Middle-row semantics unconfirmed on Gen 2
Aria documents capture_timestamp_ns as the centre of exposure of the middle row for Gen 1. The Gen 2 MPS spec says “center of exposure” without naming the row. At the ~19 ms level on profile8 that ambiguity is worth confirming with AriaOps if you need certainty.

Check yourself

Which change would have been hardest to discover?

The timestamp join. Every other failure either crashes (aspect ratio), produces visibly wrong output, or is a documented convention. That one produces a complete, well-formed dataset in which one supervision signal is silently absent — discoverable only by noticing the geometry is worse than it should be, or by instrumenting the join, which is what the fix did.

Why generalise fetch_visible_depth_map_for_RGB rather than special-case four cameras?

Because points outside the RGB frustum are already culled by project()'s mask, so an arbitrary number of cameras is safe by construction — extra ones cost a little compute and can only add coverage. A loop over a dictionary handles Gen 1's two and Gen 2's four with no per-generation branching.

Which of the nine changes are latent Gen 1 bugs rather than Gen 2 requirements?

The project() sign bug and the single-vs-batch dispatch bug were both present and wrong on Gen 1 — Gen 2 just made them more likely to fire. The timestamp convention was likewise wrong on Gen 1, just with half the magnitude. Three of the nine are fixes that benefit Gen 1 users too.

Glossary and where to go next

Cameras and geometry

pinhole model
The idealised camera: u = fx·X/Z + cx. Straight lines stay straight. What 3DGS requires.
intrinsics / K
fx, fy, cx, cy packed into a 3×3 matrix. How directions map to pixels.
focal length
In pixels, not millimetres. Governs field of view via FOV = 2·atan((W/2)/f).
principal point
cx, cy — where the optical axis meets the image. Exactly (w−1)/2 after rectification.
extrinsics / pose
Where the camera is: a rotation and a translation. Six numbers.
SE(3)
The group of rigid transforms. What sophus.SE3 holds.
c2w / w2c
Camera-to-world and its inverse. A c2w's translation column is the camera's position.
frustum
The pyramid of space a camera can see. “In frustum” means visible.
baseline
Distance between two viewpoints. No baseline, no depth.
parallax
Apparent shift of a point between two viewpoints. The signal depth is computed from.

Images and lenses

distortion
Deviation from the pinhole model caused by real glass. Straight lines come out curved.
FISHEYE624
Aria's 15-parameter camera model: 6 radial, 2 tangential, 4 thin-prism, plus focal and principal point.
rectify / undistort
Resynthesise an image as if taken by an ideal pinhole camera.
resampling
Rebuilding an image on a new pixel grid by interpolation. Every rectification is one.
upsampling
Resampling to a finer grid. Invents pixels; adds no information. The Chapter 3 trap.
vignetting
Radial darkening toward the corners, a property of the lens. Neutral on Gen 2 — the ISP already corrects it.
rolling shutter
Sensor exposes row by row, so different rows were captured at different times — and from different places.
readout time
First pixel read to last pixel read, for one frame. Read from MPS, never tabulated.
gain
Analog amplification. With exposure time, sets the frame's brightness multiplier.

SLAM and Aria

SLAM
Simultaneous localisation and mapping — solve for the camera path and the map together.
bundle adjustment
Global refinement of all poses and points at once, minimising total reprojection error.
loop closure
Recognising a previously visited place and correcting the whole trajectory backwards.
closed-loop trajectory
The loop-closed, globally consistent poses. The only one this pipeline uses.
semi-dense points
MPS's 3D point cloud — more than sparse features, less than a surface. Gaussian init and depth source.
observations
The link table: which point was seen by which camera in which frame at which pixel.
online calibration
Per-moment intrinsics, extrinsics, and readout times, re-estimated during the recording.
VRS
Meta's multi-sensor recording container. A database of timestamped records, not a video file.
MPS
Machine Perception Services — the cloud pipeline that turns a VRS into the four geometry files.
profile
A recording preset. profile8 is 2560×1920 @ 10 Hz; profile10 is 2016×1512 @ 30 Hz.

Splatting

3D Gaussian
A translucent ellipsoidal blob: mean, scales, rotation, opacity, colour.
covariance
The 3×3 matrix describing a Gaussian's shape. Factorised as R·S·Sᵀ·Rᵀ so it is always valid.
spherical harmonics
Basis functions on the sphere. Let colour vary with viewing direction. Degree 3 = 16 coefficients per channel.
alpha compositing
Front-to-back blending with running transmittance. How splats become pixels.
rasterization
Projecting and blending all Gaussians into an image. The gsplat CUDA kernel.
densification
Cloning, splitting, and pruning Gaussians during training based on screen-space gradient.
PSNR / SSIM / LPIPS
Quality metrics. Higher, higher, lower is better, respectively.

Five bugs that needed execution to find

1 · A precedence bug that let points behind the camera through

# utils/point_utils.py, before
if u < 0 or u >= w-1 or v < 0 or v >= h-1 and z > 0:
    return None, None, None, None

and binds tighter than or, so this parses as … or (v >= h-1 and z > 0). The z > 0 test is attached to the last clause only, and nothing rejects a point behind the camera. Such a point projects to a sign-flipped u,v that can land inside the image, and would be written into sparse depth with a negative depth. The vectorised branch three lines above tests z > 0 separately, which is what marks the scalar version as unintended rather than a considered trade-off.

And its measured impact was zero

Instrumented and run across all four SLAM cameras, this rejected no points at all. Obvious in hindsight: the MPS observation table only lists points a camera actually saw, so they are in front of it by construction. Independently confirmed — no negative z in any sampled sparse-depth file.

Worth sitting with, because it cuts both ways. A real bug that corrupts nothing today is still worth fixing — Stage 4 projects points that no camera observed, which is precisely the arbitrary-point case the guard exists for. But “I found a bug” and “I found corrupted data” are different claims, and only measurement tells you which one you have. Reading the code would have justified the first and tempted you into the second.

2 · project() misrouted small batches

It chose between its batched and scalar paths with if point3d.shape[-1] > 1. A batch that happened to contain exactly one point — or zero — therefore fell into the scalar path, which returns mask=None. Every batched caller then uses that None as an index. Rank distinguishes the two cases; batch size does not. The scalar path was also non-functional for genuine 1-D input, since T_w2c[:3, 3:] is a column vector and (3,) + (3,1) broadcasts to (3,3) — so it had never worked, and nothing could have depended on it.

3 · Sparse depth was computed twice per SLAM camera

Stage 3 ran once inside the rectification loop and again in the dedicated pass below it. The first result was written into a transforms.json that the second pass immediately re-read and recomputed from scratch — doubling the single most expensive stage of preprocessing to no effect. Pre-existing upstream, not introduced by the Gen 2 port.

4 · The projection loop was per-point

create_visible_depth_map called project() once per observed point: ~5,700 points across ~6,300 matched frames, each a separate Python call doing a 3×3 matrix multiply. Flattening the semi-dense map into parallel arrays once and projecting each frame in a single batched operation removes the loop entirely.

5 · densification_strategy=MCMC could not start

# model/vanilla_gsplat.py read these out of cfg.opt.mcmc_strategy …
refine_start_iter=opt.refine_start_iter,
# … but the config block defines them prefixed
mcmc_refine_start_iter: 500

Selecting MCMC raised ConfigAttributeError: Key 'refine_start_iter' is not in struct before training could begin, so that code path had never run. mcmc_refine_every was defined in the config and never passed at all.

This one turned out to be load-bearing, for a reason the next section explains.

The VRAM wall

Chapter 23 describes densification as a quality knob. On a fixed GPU it is also a survival constraint. Four attempts on a 16 GB RTX 4080 SUPER:

At SH degree 3 that implies roughly 15 million Gaussians — default densification running away on a foliage-heavy outdoor scene, compounded at iteration 10,000 where handle_rolling_shutter_start_iter begins rendering several samples per frame.

Attempt 3 is the instructive one. PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True worked exactly as advertised — reserved-but-unallocated memory fell from 7.3 GB to 189 MiB — and it still OOM'd. That result proves the remaining pressure is real allocation rather than fragmentation, which is what rules out the cheap fix and forces the expensive one.

The shape of the constraint

Peak memory is dominated by the rasteriser's Gaussian-tile intersection buffers, which scale with both Gaussian count and pixel count. On this run only one of the two was actually reduced: halving the cap from 3 M to 1.5 M took the peak from over 14 GB to about 4 GB at unchanged resolution. The cap was the fix. On a 24 GB card, raise cap_max.

Measured finding: two of attempt 4's flags did nothing

Attempt 4 also passed scene.data_factor=2 and scene.pcd_stride=2, and the run was recorded — including in an earlier version of this chapter — as having trained at half resolution. It had not. Both flags are inert: they exist in conf/config.yaml, so Hydra accepts them without complaint, but no Python code reads either one — a grep across scene/, model/ and train_lightning.py finds no consumer. Confirmed empirically: the completed run's cameras.json and its rendered test images are full 2016×1512 with fx = 1008. Accepted-but-unread flags are a Hydra failure mode worth remembering: the config schema validates the name, and nothing validates that any code listens.

The failure exits with code 0

Hydra swallows the exception's exit status. A crashed 30,000-iteration run reports success to the shell, so set -e does not catch it and a wrapper script prints its “done” message. Check for a PLY on disk, never the exit code. This is the single most expensive trap in the repository: it can cost you an hour and then tell you it worked.

The bug was real but corrupted nothing on this data — measured rejections were zero, because observed points are in front of the camera by construction. Why the PLY is not the deliverable

Isaac Sim does not read Gaussian-splat PLYs. It renders NuRec assets: a USD Volume prim carrying OmniNuRecFieldAsset children, packaged in a .usdz. NVIDIA's 3dgrut repository ships the converter.

# in the 3dgrut env, from the 3dgrut repo root
python threedgrut/export/scripts/ply_to_usd.py \
    point_cloud.ply --output_file scene.usdz

Two mechanical details cost time if you do not know them. It must run from the 3dgrut repo root, because it resolves its Hydra config relative to the script's own location. And the first run compiles 3dgrut's CUDA extensions, which takes minutes; later runs are seconds. On the reference machine the whole export — outlier filter, conversion, and a frame fix this chapter comes back to — is wrapped in scripts/bash_local/export_gen2_outside_usdz.sh.

Why RGB-only training is a hard requirement

Chapter 19 noted that the SLAM and joint colour modes write PLYs with 1 or 4 colour channels. Here is where that stops being a curiosity: the importer reads f_dc_0, f_dc_1, f_dc_2 by name, and validates that the count of f_rest_* properties equals 3 × ((max_n_features + 1)² − 1). At SH degree 3 that is 45, which is exactly what this repository writes for a 3-channel model. A 1- or 4-channel PLY fails the schema outright.

Verify the schema before you train for hours

The two sides agree on SH degree 3 → 45 f_rest properties, and the repository writes vertex as element 0 with its metadata element second — which matters because the importer reads plydata.elements[0] positionally. You can confirm the whole chain with a synthetic PLY in the right schema in under a minute, rather than discovering an incompatibility after a 30,000-iteration run.

The step nothing warns you about

Export the trained PLY directly and the resulting asset reports this bounding box:

min=[ -31402.6 -121799.3  -34125.9 ]
max=[  56617.3   44787.0  114037.8 ]

That is roughly 120 kilometres across, around a scene with 10 m of actual content. MCMC injects noise into Gaussian positions, and a small number drift arbitrarily far. Measured on this model: 1.25 % of Gaussians sit beyond 50 m, and the ~200 beyond 5 km have a median opacity of 0.011. They are invisible. They are also what defines the asset's AABB, and a 120 km AABB wrecks framing and depth precision in a USD stage.

Filtering them costs 1.25 % of the model and fixes it completely:

GaussiansAABB
raw1,500,000≈120 km

Filter about the median, not the origin

The obvious implementation — drop anything more than R from the origin — is wrong here. The MPS world origin sits wherever tracking initialised, not at the centre of the scene, so an origin-centred ball clips real content on one side and keeps junk on the other. Filter about the median Gaussian position instead. On this recording the median sat at (−0.14, −0.39, −1.30), close enough to the origin that either would have worked — which is exactly the kind of near-miss that hides the bug until a recording where it does not.

Coordinate frames: right units, one rotation too many

Half of this step is free, and the other half looked free and was not. The free half is units and content frame. The MPS world frame is gravity-aligned, Z-up, in metres — confirmed empirically on this recording: the trajectory spans about 10 m in X and Y but only 1.66 m in Z, which is head height varying as someone walks. USD's default stage convention is also Z-up in metres. The exported asset declares upAxis = Z and metersPerUnit = 1.0, and ply_to_usd.py passes dataset=None, so the exporter's optional normalising transform is skipped and the Gaussian coordinates land in the file unchanged. Scale needs no fixing, ever.

The half that was not free: 3dgrut's exporter assumes its input sits in 3dgrut's own normalised frame, which is Y-down, and it unconditionally bakes the matching Y-down-to-Z-up conversion — the rotation (x, y, z) → (−x, −z, −y) — onto the volume prim as an xformOp:transform. For a COLMAP-convention PLY that is a sensible default. This PLY is already Z-up, so it is exactly one frame conversion too many: up lands on stage −Y and the scene lies on its side. The asset first shipped that way and was even read as verified — the box at the end of this chapter shows how that happened.

The fix, and the layer it lives at

scripts/fix_nurec_usdz_frame.py rewrites that baked transform to identity inside the USDZ. It is deliberately conservative: the known 3dgrut rotation becomes identity, an already-identity transform is a no-op, and any other transform makes it refuse and exit rather than guess. scripts/bash_local/export_gen2_outside_usdz.sh now runs it automatically after ply_to_usd.py, so the exported asset loads upright, at metric scale, with no manual transform in Isaac Sim. Fixing the asset rather than the consumer is the point: File → Open, drag-and-drop, and every future referencing stage all get the correct frame for free. If a splat you import ever lies on its side, this baked rotation is the first suspect.

Recall from Chapter 2 that Aria's camera convention (X right, Y down, Z forward) matches COLMAP's, which is why there is no conversion inside the repository either. Both facts are worth being able to state, because “are your axes right?” is the first question anyone asks about an imported reconstruction.

Loading it, and a trap in how you verify

NuRec rendering is compiled into the RTX Hydra delegate — on Isaac Sim 5.1 it is present with no extra extension to install. Open the .usdz with File → Open, or drag it onto an existing stage to reference it in, then select an RTX renderer. It will not appear under the preview delegate. Frame the prim rather than the stage: the splat sits at MPS world coordinates, which are not centred on the origin. And expect the content to look small when you do: framing fits the ±50 m outlier-filter bounding box, while about 85 % of the splat's opacity mass sits within 10 m of the scene centre. That is a framing artifact — the price of the sparse low-opacity shell the 50 m filter keeps — not a unit error. Zoom in.

Neither stdout nor the exit code is evidence

Kit captures Python stdout into its own logger and force-exits on shutdown. A headless verification script here ran to completion, printed nothing at all, and exited 0 — which proves only that a process ended. Write results to a file and read the file. Both of this chapter's exit-code traps have the same moral as Chapter 27's Hydra one: on this stack, success is something you confirm by looking at an artefact, never by looking at a return value.

Written to a JSON report, the actual verification looks like this:

{ "ok": true, "up_axis": "Z", "meters_per_unit": 1.0,
  "nurec_prim_count": 2,
  "volume_frame_is_identity": true,
  "world_aabb_min": [-48.06, -48.53, -49.76],
  "world_aabb_max": [ 49.07,  48.66,  47.63] }

Both field prims resolved, the composed volume transform is identity, and the world bounds equal the filtered PLY's own bounds axis for axis — the asset renders at the right scale and the right orientation, which is a much stronger statement than “the file opened”.

How a sideways asset once passed this check

An earlier version of this verification had no volume_frame_is_identity field, and the broken asset — baked rotation still live — reported bounds of [-49.07, -47.63, -48.66] … [48.06, 49.76, 48.53]. That looked plausible and was read as success. It is the correct box pushed through (x, y, z) → (−x, −z, −y): a rotation of a near-symmetric bounding box is invisible to a magnitude check. The diagnosis came from comparing the world bounds against the PLY's axis for axis — they matched the rotated pattern digit for digit — and scripts/isaacsim_load_splat.py now reports the composed volume transform outright, so a re-exported asset that skips the frame fix fails the smoke test instead of being discovered sideways in a viewport.

What a splat is not

A NuRec splat renders as a volume and has no collision geometry. Nothing will stand on it, bump into it, or cast a shadow onto it as physics. For a robotics environment you add collision proxies separately — typically a mesh or simple primitives derived from the semi-dense point cloud you already have. Worth deciding early whether you need a photometric backdrop or a physical environment, because they are different pieces of work and the splat only supplies the first. Chapter 31 is that second piece of work, measured.

Why filter about the median Gaussian position rather than the origin?

Because the MPS world origin is wherever SLAM tracking initialised, which has no relationship to the centre of the captured scene. An origin-centred radius therefore clips real content on the far side and retains outliers on the near side. On this recording the median happened to be about 1.4 m from the origin so both would have worked — which is precisely why the distinction is easy to get wrong and only fails later.

You export a splat trained with camera.camera_name="slam" and the converter rejects it. Why, and what is the fix?

The monochrome model writes one colour channel, so the PLY has f_dc_0 only and 15 f_rest properties instead of 3 and 45. The importer requires three named DC components and validates the f_rest count against SH degree. There is no fix at export time — retrain in RGB mode. The SLAM cameras still contribute through preprocessing, where they generate the RGB sparse depth.

The full chain

.vrs + MPS → preprocess → train → .ply → filter → convert → frame fix → .usdz → Isaac Sim. The repository covers everything from preprocess through the frame fix. The two ends — capture technique in Chapter 25, and the final load — are where a reconstruction stops being an experiment and becomes something another program can use. And the splat is still only half the deliverable: Chapter 31 builds the surface a robot can actually stand on.

Chapter 30 / Part VIII · The bigger picture / 25 min

Designing any pipeline: the four questions

Strip the Aria specifics away and the pipeline you now know is one instance of a schema: four questions, asked in order, whose answers dictate every stage. Learn the questions and you can design the equivalent pipeline for a drone, a phone, or a robot dog — without a recipe to copy.

The temptation after learning one pipeline deeply is to treat its shape as the shape. It is not. Every stage you have studied exists as the answer to a question about this particular device and this particular consumer — change the answer and the stage changes or disappears. Here are the questions, each with the Aria answer as the worked case.

Question 1 — what is my camera?

Are the intrinsics known, or must you calibrate? Which distortion model does the lens follow? Is the shutter global or rolling? The answers decide your entire front end. Aria's answer: intrinsics known per-moment from online calibration, a FISHEYE624 fisheye, and a rolling-shutter RGB sensor. Hence the two front-end decisions that shaped Parts III–IV: rectify everything to pinhole first, because nearly every downstream tool — the rasteriser included — assumes pinhole (Chapters 3 and 7); and model the shutter explicitly, because at head speed 10 ms of readout is visible geometry (Chapters 4 and 21). A global-shutter pinhole-ish camera would delete both pieces of work.

Question 2 — where are my cameras?

Poses come in three grades, and each grade names its own pipeline. None — structure-from-motion (COLMAP) must solve them from the images. Approximate — GPS, odometry, a consumer IMU: use them as initialisation and refine with bundle adjustment, Chapter 9's global photometric clean-up. Good — a tracking system you trust: fix them and skip pose solving entirely. Always ask two follow-ups: in what coordinate frame, and at what scale? Aria's answer: good — MPS closed-loop poses, metric and gravity-aligned, which is why nothing in this repository ever solves for a pose.

Gauge freedom: why photos alone cannot pin the world

Images by themselves constrain only relative geometry. Take a finished COLMAP solution — every pose and every point — and rotate it, translate it, and scale it by one global factor: seven numbers. Every image reprojects identically; no photograph can tell the difference. This is called gauge freedom, and it means monocular structure-from-motion picks its world frame and its scale arbitrarily, because nothing in the data prefers one choice.

The practical consequence: if you let COLMAP solve your poses, anything else you build — a splat, a mesh, a robot path — lives in COLMAP's arbitrary frame, and you must later estimate that 7-degree-of-freedom transform from noisy data to align it with the real world. This pipeline avoids the problem instead of solving it: MPS poses are metric and gravity-aligned, both of the project's products are built in the same MPS world frame, and alignment never becomes a step. That is the single most defensible design decision in the project, and it came from answering this question before writing any code.

Question 3 — what representation does the consumer need?

Physics needs surfaces — something a ray or a wheel can intersect: a triangle mesh, a heightfield (a grid of floor heights), a signed distance field. Rendering needs appearance — something that produces the right pixels from any viewpoint: a splat, a NeRF. Neither substitutes for the other, and that sentence is this project's two-track architecture: the splat track you have studied for twenty-eight chapters, and the mesh track of Chapter 31. If your consumer needs both, you are building both, and it is better to know that on day one.

Question 4 — how do I measure success?

Decide before building, because the measurement determines what you must hold back. For appearance: held-out photographs and PSNR / SSIM / LPIPS — the every-8th-frame protocol of Chapter 23, which costs nothing but discipline. For surfaces the photometric loss cannot judge at all, so you need geometry the surface was not built from — here, the MPS semi-dense points — and, above everything, a task metric: Chapter 31's drive test, where a robot either falls through the floor or does not. Aria's answer: all three, and the ranking of candidate meshes changed once the task metric ran — which is exactly why paper metrics are called proxies.

The checklist, applied cold: drone photos with GPS

Suppose tomorrow someone hands you five hundred drone photographs with GPS tags and asks for a splat of the site. Ask the questions:

Q1 · camera
Intrinsics roughly known from EXIF; calibrate properly or let bundle adjustment refine them. Modest lens distortion, standard models. Assume you must check the shutter, not assume it.
Q2 · poses
GPS plus a crude IMU: the approximate branch. Use them to initialise, refine with bundle adjustment — and because GPS pinned the scale, the result stays metric with no alignment step. Skipping the refinement wastes the photos; discarding the GPS and running blind SfM throws away the metric anchor gauge freedom cannot restore.
Q3 · representation
A splat — so the training consumer needs pinhole intrinsics, a per-image pose, and sparse points for initialisation: a COLMAP model or a transforms.json, which you now know how to read field by field.
Q4 · success
Hold out every 8th image before training starts; report held-out PSNR. If a mesh is ever requested, keep independent geometry — the refined sparse points — for judging it.

Notice what just happened: the checklist designed the pipeline. A calibration step, a refine-not-solve pose stage, a metric splat with no alignment step, and an evaluation protocol — decided in four paragraphs, before a line of code, each decision defensible out loud because it is the answer to a named question.

Check yourself

Phone video, no pose information at all. Which branch of Question 2 are you on, and what ambiguity do you accept?

The none branch: structure-from-motion must solve the poses. You accept gauge freedom — the reconstruction's frame and scale are arbitrary. Nothing downstream may assume metres or a known up-axis unless you add outside information: a known-size object in frame, IMU gravity, a measured distance between two points.

Why does fixing poses remove the alignment step, rather than merely improving it?

Because every product is then built in the same, already-meaningful frame. The 7-DOF transform between your splat's frame and your mesh's frame is identity by construction — there is nothing left to estimate, so there is no estimation error to carry. With solved poses that transform is a real unknown that must be recovered from noisy data, and its error contaminates everything downstream.

A stakeholder asks for “a 3D model we can render and collide with”. What does Question 3 tell you to say?

That this is two representations, not one — an appearance product and a surface product — and therefore two tracks of work with different algorithms and different evaluations. Promising one artifact for both is how a splat ends up being asked to hold up a robot. Plan both from the start, and share the pose and frame decisions (Question 2) so the two products drop into the same world without alignment.

A splat is not a surface

The trained PLY is 1.5 million ellipsoids — each one a position, three scales, a rotation, an opacity and colour coefficients. There are no vertices, no edges, no faces, and no flag that adds them. A renderer can composite the ellipsoids into a picture; a physics engine has nothing to intersect. Ask the splat “where is the floor?” and there is no answer inside it — translucent blobs have no inside and no top. Mesh extraction is always a separate step, with its own errors and its own evaluation.

The standard recipe: depth, TSDF, marching cubes

Every route to a surface here follows the same three moves. First, obtain depth images from many known poses — either rendered out of the trained splat (a splat has no surface, but it can still produce an expected depth per pixel by blending along each ray) or measured directly by a sensor.

Second, fuse them into a TSDF — a truncated signed distance function. Divide space into small voxels (2 cm here); in each voxel store the signed distance to the nearest observed surface — negative behind it, positive in front — truncated to a narrow band (8 cm) so that far-away surfaces do not smear the grid. Every depth image carves its rays into the grid, and averaging hundreds of views cancels the noise of any single one.

Third, run marching cubes: walk the grid and stitch triangles wherever the stored distance crosses zero. Out comes a triangle mesh, in the same MPS world frame as everything else.

The property that drives everything in this chapter: a voxel nobody observed produces no surface — a hole. So the metric that mattered was floor coverage: rasterise the walked corridor into 10 cm cells and ask, for each cell, whether a downward ray hits mesh within ±15 cm of the expected floor height. A robot survives most kinds of mesh error; it does not survive a hole.

Splat depth, 2DGS. Same recipe, different primitive: flat oriented disks — surfels — instead of ellipsoids. A disk has a tangent plane, so depth comes from exact ray–disk intersection and training can add geometry regularisers that force disks to lie flat on the surfaces they render. Stereo depth. The two front SLAM cameras fire at the same instant from viewpoints 135 mm apart — a stereo pair, with the baseline read out of the calibration rather than assumed. A learned matcher (FoundationStereo) finds each pixel's disparity — how far a feature shifts between the two views — and depth follows from Z = f·B/d. Best observed floor by a wide margin: 0.864 coverage, largest hole under a square metre, 2.18 cm median error. But the physics bites at range: depth error grows as Z²·σd / (f·B), which on this 512-pixel, 13.5 cm rig is roughly a centimetre at 1 m, 30 cm at 5 m, and 1.2 m at 10 m. The fusion therefore cuts depth at 4 m, and the route is deliberately blind beyond that.

Trajectory floor. No cameras at all — the demonstrator is the sensor. Wherever the head went, there was walkable floor about one eye-height below it, so the closed-loop trajectory minus a calibrated eye height (1.67 m for this wearer, fitted by casting rays from the trajectory down onto a recovered mesh) is itself a floor surface: coverage 0.978, largest hole 0.48 m². Complete along everything actually walked, and containing no obstacles whatsoever — a floor prior, not a scene. Its job is filling the other routes' holes: fused into the stereo mesh, it lifted coverage to 0.970 with a 0.40 m² largest hole while keeping stereo's obstacles. (Its error column is blank above because the MPS cloud is dominated by walls and foliage, which a floor-only mesh is not trying to model.)

The fifth route is left for you. Photogrammetry — COLMAP's multi-view stereo with the MPS poses held fixed — was designed but deliberately not run. It differs from the SLAM-pair stereo in one variable: where the baseline comes from. Your own motion supplies it — metres rather than a fixed 13.5 cm — so f·B grows and far surfaces stay measurable. The price is that the matched views are seconds apart instead of simultaneous: the scene must hold still, and matching needs texture to lock onto. Expect it to lose to the stereo pair on blank floor, and possibly beat everything on far walls. Running it and adding the row to the table above is the single best exercise this course can leave you.

The final judge: the drive test

Every number in the table is a proxy. The requirement is behavioural: load the splat as the visuals and the mesh as invisible collision geometry in Isaac Sim — both in the MPS world frame, so they drop onto each other with no registration — then drive a wheeled robot along the demonstrator's real path, waypoint by waypoint down the closed-loop trajectory, and count what actually goes wrong: fall-throughs, where the robot passes below the floor, and phantom collisions, where it stalls or wedges against geometry that is not really there.

One measured example of why the proxy is not enough. A fused mesh passed every per-cell floor check — and the drive beached the robot at one spot on the path. The fusion had patched a strip of rejected cells at the floor prior's height, next to kept mesh sitting a step higher: a trench one wheel-track wide, with every individual cell inside tolerance. A per-cell metric cannot see a step between cells; a differential-drive robot finds it immediately. The consumer's failure modes define the test — which is Question 4 of Chapter 30, closing the loop.

Check yourself

2DGS's largest floor hole sits in exactly the same region as 3DGS's. Why is that expected rather than a coincidence?

Because holes come from the observations, not the primitive. Both routes rendered depth from the same trained poses over the same photographs, so a region that was poorly constrained — steep grade, little texture, few viewpoints — is poorly constrained for both. The better primitive shrinks the hole (19.94 → 8.86 m²) because its depth is crisper where evidence exists; it cannot conjure surface where no camera supplied evidence.

Why is the stereo pair blind past a few metres, while photogrammetry need not be?

Depth error grows as Z²·σd/(f·B), and the pair's baseline B is welded to the glasses at 13.5 cm — so error reaches metre scale by 10 m and no matcher can fix it. Photogrammetry's baseline is your own motion, metres wide, which pushes the same error curve far out. The exchange: its views are seconds apart, so the scene must be static and textured enough to match — exactly the conditions the simultaneous pair never has to worry about.

The best fused mesh scores 0.97 coverage. Why run a drive test at all?

Because coverage is a per-cell judgement against each cell's own expected height, and some failure modes live between cells: a curb-like seam where adjacent cells are individually in tolerance but step past each other beaches a robot while scoring perfectly. The drive test measures the deliverable's actual job — a robot traversing the demonstrated path — and it found exactly such a seam that every paper metric had passed.
